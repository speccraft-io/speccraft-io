[Polygraph](https://github.com/cognitive-fab/polygraph) finds bugs in code that keeps state, like workflows,
checkout flows and reducers (a function `(state, action) => newState`, as in Redux). It is a CLI and a Claude Code
plugin. It is experimental: its own README calls it a consistency check, not a proof.

## The idea

It is the same kind of check as [TLA+](/tools/tla-plus): try every action in every state, and check your rules in each
state. The difference: you do not write the model. An LLM copies your code into a JavaScript state machine, called the
**spec**. It works in three steps:

1. **The LLM writes the spec** from your code.
2. **Replay:** your real code runs a few scripted sessions, and every call is recorded. The spec must give the same
   result for each call. This tells you if you can trust the spec.
3. **Model check:** starting from the first state, Polygraph tries every action with every data value you list, in
   every state it can reach, and checks your rules in each state.

Replay alone cannot find a bug: the spec copies the code, bug included, so the two agree. Only the model check finds
it, and only against rules you write. That is why the rules come from you.

Polygraph has its own model checker, written in JavaScript. It does not use TLA+. As an option, `--tla` turns the spec
into TLA+ and checks it with TLC, the TLA+ model checker.

### What SAM is

The spec must be written in SAM (State-Action-Model), a pattern Polygraph's author, Jean-Jacques Dubray, published in
2016. It is close to a Redux reducer, split in two: an **action** turns an event into a proposed change, and an
**acceptor** accepts it and sets the next state, or rejects it with a name.

```js
// cart.ts, a reducer: one function computes and decides
case 'APPLY_COUPON':
  if (action.code !== 'SAVE5') return state;
  if (state.items * PRICE < MIN_SPEND) return state;
  return { ...state, coupon: 'SAVE5' };

// specs/cart-sam.js, SAM: the action proposes, the acceptor decides
actions: { APPLY_COUPON: { action: (data = {}) => ({ ...data }) /* ... */ } },
acceptors: {
  APPLY_COUPON: (model) => (proposal, { reject, next, unchanged }) => {
    if (proposal.code !== 'SAVE5') return reject('unknown-code');
    if (model.items * 1000 < 2000) return reject('below-minimum');
    next.coupon = 'SAVE5';
    unchanged('items');
  },
},
```

Polygraph adds strict rules: every state field is declared, every rejection has a name, and each action lists the data
values to try (`domain`). That tells the model checker exactly what to try, and tells replay why the spec said no.

SAM is not widely used; most JavaScript code uses Redux, Zustand or [XState](/vs/xstate). Your own code does not have
to use it. Think of SAM as the file format of Polygraph's specs.

## Using Polygraph

The code below is in
[formal-methods-samples/polygraph-coupon](https://github.com/speccraft-io/speccraft-io/tree/main/formal-methods-samples/polygraph-coupon).
We ran it with Polygraph 8.3.0 on Node 24. Normally an LLM writes the spec, which needs an Anthropic API key. We wrote
the spec by hand instead, in the format the LLM writes. All output below is from our run.

### The problem

<Short>The minimum spend is checked when the coupon is applied, not when an item is removed.</Short>

A shop's cart is a reducer: it takes the cart and an action, and returns the new cart. Every item costs 10.00. The `SAVE5` coupon needs a total of at least 20.00:

```ts
// cart.ts (shortened)
export function cart(state: Cart, action: CartAction): Cart {
  switch (action.type) {
    case 'ADD_ITEM':
      if (state.items === MAX_ITEMS) return state;
      return { ...state, items: state.items + 1 };
    case 'REMOVE_ITEM':
      if (state.items === 0) return state;
      return { ...state, items: state.items - 1 };
    case 'APPLY_COUPON':
      if (action.code !== 'SAVE5') return state;
      if (state.items * PRICE < MIN_SPEND) return state;
      return { ...state, coupon: 'SAVE5' };
  }
}
```

The bug: the minimum is checked only when the coupon is applied. Add two items, apply the coupon, remove one item,
and the coupon stays on a 10.00 cart.

### The four files

<Short>Four files: a contract, recorded calls, a spec, and your rules. The LLM writes the spec; you write the rules.</Short>

Who writes what:

- **Contract:** you, or Claude writes a draft for you to check.
- **Recorded calls:** in Claude Code, the agent records them. With the CLI, you wrap your reducer once.
- **Spec:** the LLM. You do not write it.
- **Rules:** you. Polygraph can suggest rules, but only you know what the code should do.

**1. The contract** (`contract.json`) describes the state and the actions. It also names special cases in the code.
Here they are the four cases where an action does nothing, like `below-minimum`:

```json
// contract.json (shortened)
{
  "stateKeys": [
    { "name": "items", "type": "number (0 to 3, each item costs 10.00)" },
    { "name": "coupon", "type": "'SAVE5' | null" }
  ],
  "initState": { "items": 0, "coupon": null },
  "actions": {
    "ADD_ITEM": { "dataFields": {} },
    "REMOVE_ITEM": { "dataFields": {} },
    "APPLY_COUPON": { "dataFields": { "code": "string" } }
  },
  "specialRules": [
    { "name": "below-minimum", "note": "APPLY_COUPON under a 20.00 subtotal leaves the cart unchanged.", "whenAction": "APPLY_COUPON" }
    // cart-full, cart-empty and unknown-code look the same
  ]
}
```

**2. The recorded calls** (traces). `tapReducer` wraps your reducer. Every call to the wrapped reducer is saved as one
line in `traces/sessions.ndjson`. The sample runs a few lists of cart actions through it.
Wrap a copy of your code, not the real one: the wrapper writes to a file on every call, so it must not reach production.

```ts
// record-traces.ts (shortened)
const traced = tapReducer(cart, (s: Cart) => s, 'traces/sessions.ndjson');
for (const session of sessions) session.reduce(traced, emptyCart);
```

Each line has the cart before the call (`pre`), the action and its data, and the cart after (`post`):

```text
{"pre":{"items":1,"coupon":null},"action":"APPLY_COUPON","data":{"code":"SAVE5"},"post":{"items":1,"coupon":null}}
```

Here the coupon is applied to one item, and the cart does not change, because 10.00 is below the minimum.

**3. The spec** (`specs/cart-sam.js`) is the cart logic again, written by the LLM in SAM. In this example we wrote it by hand, because we ran without an API key. It copies
the code as it is, bug included. For each action, `domain` lists the data to try, and the acceptor computes the next
state or rejects the action with a name from the contract:

```js
// specs/cart-sam.js (shortened)
actions: {
  REMOVE_ITEM: { action: (data = {}) => ({ ...data }), schema: {}, domain: [{}] },
  APPLY_COUPON: { /* ... */ domain: [{ code: 'SAVE5' }, { code: 'SAVE10' }] },
},
acceptors: {
  REMOVE_ITEM: (model) => (proposal, { reject, next, unchanged }) => {
    if (model.items === 0) return reject('cart-empty');
    next.items = model.items - 1;
    unchanged('coupon');
  },
},
```

**4. The rules** (`invariants.mjs`) must be true in every state. You write these yourself. The spec is copied from the
code, so it can only say what the code does, not what it should do.

```js
// invariants.mjs
export const stateInvariants = [
  { name: 'coupon-needs-minimum-spend', pred: (s) => s.coupon === null || s.items * 1000 >= 2000 },
];
```

### Running it

<Short>Replay passes. The model check finds the bug in 4 steps.</Short>

First, replay the recorded calls through the spec:

```sh
node node_modules/@cognitive-fab/polygraph/scripts/verify.mjs --contract contract.json --traces traces \
  --specs specs --out out
```

```text
15/15 windows consistent across 1 spec(s).
findings: 0 spec-error, 0 code-finding/contract, 0 unscoreable-all
```

All 15 recorded calls match, so the spec does what the code does. But none of the recorded calls hit the bug.

Then run the model check. In every state it can reach, it tries every action with every value in `domain`:

```sh
node node_modules/@cognitive-fab/polygraph/scripts/check.mjs --spec specs/cart-sam.js --contract contract.json \
  --invariants invariants.mjs
```

```text
states explored: 8
rejections explored: below-minimum ×4, cart-empty ×2, cart-full ×2, unknown-code ×8
1 invariant violation(s):

  ✗ coupon-needs-minimum-spend [state] — reachable state violates the rule
    counterexample (shortest path from init):
      init            {"items":0,"coupon":null}
      ADD_ITEM({}) -> {"items":1,"coupon":null}
      ADD_ITEM({}) -> {"items":2,"coupon":null}
      APPLY_COUPON({"code":"SAVE5"}) -> {"items":2,"coupon":"SAVE5"}
      REMOVE_ITEM({}) -> {"items":1,"coupon":"SAVE5"}
```

It found the bug: the shortest list of actions that breaks the rule. You can run the same actions on the real
reducer to see the bug.

### Fixing the bug

<Short>Remove the coupon when the total drops below the minimum: no rule broken. Replay alone could not see the difference.</Short>

When an item is removed and the total drops below the minimum, the coupon is removed too:

After recording the calls and writing the spec again from the fixed code, the model check passes:


## Project layout and CI

<Short>Commit the contract, the spec and your rules. CI records new traces, replays them and runs the model check. No API key.</Short>

```text
./
├── .github/workflows/ci.yml
├── src/cart.ts                    the reducer
└── polygraph/
    ├── contract.json              state and actions
    ├── invariants.mjs             your rules
    ├── specs/cart-sam.js              written by the LLM, committed
    └── record-traces.ts           runs sessions through tapReducer
```

`traces/` and `out/` are not committed: CI makes them from the current code. Replay and the model check need no API
key, so CI runs them on every push:

<details>
<summary>The CI workflow: <code>.github/workflows/ci.yml</code> (7 lines)</summary>

```yaml
# .github/workflows/ci.yml (steps)
- run: npm ci
- run: node polygraph/record-traces.ts
- run: npx polygraph --contract polygraph/contract.json --traces traces --specs polygraph/specs --out out
# Replay exits 0 even when calls do not match, so check its report.
- run: node -e "const s = require('./out/findings.json').summary; if (s.consistent !== s.windows) process.exit(1)"
- run: node node_modules/@cognitive-fab/polygraph/scripts/check.mjs --spec polygraph/specs/cart-sam.js --contract polygraph/contract.json --invariants polygraph/invariants.mjs
```

</details>

What fails when:

- **The code changes and the spec does not:** the report step. The new traces no longer match the spec.
- **A change breaks a rule:** `check.mjs`, with the shortest list of actions to the bug.

## Making changes

<Short>Change the code, record, have the LLM write the spec again, run both checks, commit.</Short>

1. Change the reducer.
2. Record the traces again, and run replay. Calls that no longer match show where the spec is out of date.
3. Have the LLM write the spec again. This step needs the API key.
4. Run the model check. If the change adds a rule, add it to `invariants.mjs` first.
5. Commit the code, the spec and the rules together.

A new action or state field goes into `contract.json` first, then into the recording script, so the traces cover it.

## Compared with other tools

- **[TLA+](/tools/tla-plus) and [Quint](/tools/quint):** the same kind of check, but you write the model yourself, in
  another language. Much older and much more used. All three find a wrong state that some order of actions can reach,
  with the shortest list of steps to it. TLA+ and Quint also cover:
  - **Concurrency:** several processes, messages, crashes and retries, in every order. Polygraph checks one machine
    taking one action at a time. For deep bugs in concurrent or distributed systems, its README says to use Specula.
  - **Liveness:** "every order is eventually paid or refunded". Polygraph checks rules on one state or one step only.
  - **Designs before code:** Polygraph needs code to copy.

  Polygraph has one thing they do not: replay checks that the model matches your real code.
- **[XState](/vs/xstate), [tla-precheck](/vs/tla-precheck), [stateproof](/vs/stateproof):** your code is the machine,
  so there is no copy to keep in step. But you must write the code their way first. Polygraph is for code that is
  already written.
- **[fast-check](/vs/fast-check):** runs your real code with random lists of actions. It tries many orders, not all,
  but it tests the code itself, not a copy.
- **[Specula](https://github.com/specula-org/Specula):** a research project with the same three steps, but in TLA+.
  Its August 2026 paper reports 249 bugs in 48 real projects (MongoDB, etcd and others); maintainers confirmed 68 of
  them. Polygraph's own README calls it the closest project, and ahead on evidence.

## Strengths

- **Starts from your code.** An LLM writes the spec from code you already have.
- **Checks every state it can reach.** Not only the calls you recorded. Here replay missed the bug and the model
  check found it.
- **Checks the spec against your real code.** Replay shows if the spec does something your code does not.
- **Gives the steps to the bug.** You get the shortest list of actions that breaks a rule.

## Limitations

- **You write the rules.** The spec is copied from your code, so it has the same bugs. Only your rules catch them.
- **It checks the spec, not your code.** Replay compares them only on the calls you recorded. Timing and async code
  are covered only if the spec includes them.
- **Only the values you list.** Numbers, amounts and strings are checked only at the values in `domain`. A bug at
  another value is not found.
- **Code must run on its own.** Code that needs a database or a network needs test doubles first. In Claude Code, the
  agent can build them.
- **Experimental, and needs an LLM.** Its README says it is not a proof and not peer-reviewed. Writing the spec needs
  an Anthropic API key and a strong model; the README recommends Opus 5 or better.
- **Young.** The GitHub repo started in July 2026 and the npm package in September 2026. Almost all commits come from
  one account. One production bug is confirmed outside the project, and the paper behind it is the author's own
  preprint.
