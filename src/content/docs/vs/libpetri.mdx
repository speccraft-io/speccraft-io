[libpetri](https://github.com/debe/libpetri) is a library for writing async code as a graph of steps. You say what
each step needs before it can run, and what it hands on when it is done. libpetri runs the graph as your real code.
It can also check the same graph before it runs, for example that a connection taken from a pool always comes back,
or that nothing waits forever.

You do not keep a separate model next to the code: the graph is the code.

<Short>You write the flow as a graph of steps; libpetri runs it and checks it. Here: a report whose failed query never gives its connection back.</Short>

## Using libpetri

The code below is in [formal-methods-samples/libpetri-fan-out](https://github.com/speccraft-io/speccraft-io/tree/main/formal-methods-samples/libpetri-fan-out).

### The problem

<Short>A failed query keeps its connection. After one failure the pool has one connection, and the next report waits forever.</Short>

A report runs two queries at once, orders and invoices. Each query takes a connection from a pool of two and gives it
back when it is done. The happy-path test passes: one report, both connections back.

The bug is the one a missing `finally` causes: the connection goes back only when the query succeeds. When a query
throws, its connection is gone. A report needs two connections, so after one failure the next report never starts,
and nothing reports an error.

The rule: when there is nothing left to do, both connections are back in the pool.

### Install and set up

```sh
npm install libpetri
brew install z3   # or any z3 4.8.0+ on PATH
```

The checker uses the `z3` solver for big graphs. This graph is small, so it is checked without z3 (see
[Running it](#running-it)).

### Writing the flow

<Short>A slot holds values. A step says which slots it reads from and writes to, then runs an async function.</Short>

```ts
// report.ts (shortened)
// A "place" is a slot that holds values: pending requests, free connections, results.
export const requests = place<string>('requests');
export const pool = place<Conn>('pool');           // the free connections
export const ordersJob = place<Conn>('ordersJob'); // a connection in use by the orders query
export const ordersRows = place<string[]>('ordersRows');
export const failed = place<Error>('failed');
// ... invoicesJob, invoicesRows, reports, errors

// A "transition" is a step. It runs when every slot it reads from has a value.
// This one takes a request and two free connections, and starts both queries.
const start = Transition.builder('start')
  .inputs(one(requests), exactly(2, pool))
  .outputs(and(outPlace(ordersJob), outPlace(invoicesJob)))
  .action(async (ctx) => {
    const [a, b] = ctx.inputs(pool);
    ctx.output(ordersJob, a!);
    ctx.output(invoicesJob, b!);
  })
  .build();
```

Each query is a step too. `xor` means the step writes to one of two places: the rows on success, the error on
failure.

`finish` puts the two results into a report, and `fail` turns a failed query into an error. After `start`, both
queries can run, and their promises run at the same time.

### Running it

<Short>One call, 3 ms: four steps end with one connection in the pool and a report that can never start.</Short>

The check is a call in a test. `quiescentCount([pool], 2, 2)` is the rule: whenever there is nothing left to run,
the pool holds exactly two connections.

```ts
// report.libpetri.test.ts (shortened)
const result = await SmtVerifier.forNet(reportNet(db))
  .initialMarking((m) => m.tokens(requests, 2).tokens(pool, 2)) // start: 2 requests, 2 free connections
  .property(quiescentCount([pool], 2, 2))
  .verify();

result.verdict;                   // { type: 'violated' }
result.counterexampleTransitions; // [ 'start', 'queryInvoices', 'queryOrders', 'fail' ]
```

The steps that break the rule, with how many values each slot holds after each step:

```text
{pool:2, requests:2}
{invoicesJob:1, ordersJob:1, requests:1}
{invoicesRows:1, ordersJob:1, pool:1, requests:1}
{failed:1, invoicesRows:1, pool:1, requests:1}
{errors:1, invoicesRows:1, pool:1, requests:1}
```

The last line is stuck: the second request needs two connections and the pool has one. The graph has only 48 possible
states, so libpetri tried all of them, without z3. With that turned off (`.enumerationMaxClasses(0)`), z3 finds the
same steps in 35 ms.

The test also runs the real code, with a database whose invoices query throws. It ends the same way:

```ts
const result = await new BitmapNetExecutor(reportNet(failingDb), initialTokens).run();
result.tokenCount(pool);     // 1
result.tokenCount(requests); // 1, never started
```

### Fixing the bug

<Short>Give the connection back on failure too. Proven in 4 ms, and the report says why: every connection is in the pool or in use by a query.</Short>

The failure branch gives the connection back too:

The same check now returns `proven`. With z3, the report also shows why:

```text
Phase 3: Computing P-invariants...
  Found: 2 P-invariant(s)
  Structurally bounded: YES
  errors + failed + invoicesJob + invoicesRows + ordersJob + ordersRows + 2*reports + 2*requests = 4
  invoicesJob + ordersJob + pool = 2
...
PROVEN (state equation): Quiescent count: exactly 2 across {pool}
```

The line `invoicesJob + ordersJob + pool = 2` is a sum that never changes: every connection is either in the pool or
in use by a query. In the buggy version the same sum also had `failed` and `errors` in it, so a connection could end up
there and never come back.

## Project layout and CI

<Short>The graph is the code. Commit it and the test; CI runs Vitest. Install z3 in CI once graphs get big.</Short>

```text
./
├── .github/workflows/ci.yml
├── report.ts                 the flow: slots, steps and their functions
└── report.libpetri.test.ts   runs the flow and checks it
```

Nothing is generated. The test checks the same code that runs in production.

<details>
<summary>The CI workflow: <code>.github/workflows/ci.yml</code> (7 lines)</summary>

```yaml
# .github/workflows/ci.yml (steps)
- uses: actions/setup-node@v7
  with:
    node-version: 22
- run: sudo apt-get install -y z3
- run: npm ci
- run: npm test
```

</details>

What fails when:

- **A connection can be lost, or a request can wait forever:** the check, with the steps that lead there.
- **z3 is missing and the graph is too big to try every state:** the verdict is `unknown`, with the reason. Test for
  `proven`, not for "not violated".
- **A step's function throws instead of writing a result:** the run test. The checker does not read the code inside
  the functions.

## Making changes

<Short>Change the flow, run the test, commit.</Short>

1. Change the flow: a new slot or step, or what a step reads and writes.
2. If a step's function changes, check it still writes to the places the step says it writes to. The checker trusts
   what the step says.
3. Add a rule for anything new: a limit on a slot, two slots that must never both hold a value, a count when nothing
   is left to run.
4. Run `npm test`.

## Strengths

- **The checked code is the running code.** There is no copy to keep in sync.
- **Pools and limits are visible.** A pool, a budget or a permit is a slot with a number of values. A leak or a wait
  that never ends breaks a rule you can check.
- **A proof says why.** A proven result can show the sum that never changes, like "every connection is in the pool or
  in use".
- **Small graphs need no solver.** The checker tries every state and shows the real steps.
- **Used in production.** It runs the author's production commerce assistant at Otto.
- **Checked itself.** The same spec is built in Java, TypeScript and Rust, each with its own tests. Proofs in Lean
  show the checker does not miss what the runtime can do.

## Limitations

- **You write the flow as a graph.** Existing `async` code has to be rewritten as slots and steps. That is a bigger
  change than adding a spec next to the code.
- **The checker trusts each step.** It reads what a step says it reads and writes, not the code inside it. A function
  that skips a write it promised is caught only by running it.
- **Values and time are not checked.** The checker counts how many values each slot holds, not what they are, and
  ignores timeouts. A proof still holds with timeouts, but a failing trace can be one that a timeout would stop.
- **New terms to learn.** Places, transitions, and the kinds of inputs and outputs take time if you have not used
  [Petri nets](/concepts/petri-nets).
- **Big graphs need z3** on your machine and in CI.
