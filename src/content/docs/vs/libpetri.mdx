[libpetri](https://github.com/debe/libpetri) runs [Petri nets](/concepts/petri-nets) as programs. Places hold typed
tokens, transitions run async actions, and arcs say what each transition takes and gives. The runtime executes the
net, and the same net goes to a checker: deadlock freedom, mutual exclusion, place bounds, and token counts at rest.
There is no separate model to keep in sync with the code.

<Short>The net is both the program and the model. Here: a report whose failed query never gives its connection back.</Short>

## Using libpetri

The code below is in [formal-methods-samples/libpetri-fan-out](https://github.com/speccraft-io/speccraft-io/tree/main/formal-methods-samples/libpetri-fan-out).

### The problem

<Short>A failed query keeps its connection. After one failure the pool has one connection, and the next report waits forever.</Short>

A report runs two queries at once, orders and invoices. Each query takes a connection from a pool of two and gives it
back when it is done. The happy-path test passes: one report, both connections back.

The bug is the one a missing `finally` causes: the connection goes back only when the query succeeds. When a query
throws, its connection is gone. A report needs two connections, so after one failure the next report never starts,
and nothing reports an error.

The rule: once nothing can run, both connections are back in the pool.

### Install and set up

```sh
npm install libpetri
brew install z3   # or any z3 4.8.0+ on PATH
```

The runtime has no dependencies. The checker runs the `z3` executable as a separate process. Small nets like this one
are decided without it (see [Running it](#running-it)).

### Writing the net

<Short>Places are typed; a transition says its inputs and outputs, then runs an async action.</Short>

```ts
// report.ts (shortened)
export const requests = place<string>('requests');
export const pool = place<Conn>('pool');
export const ordersJob = place<Conn>('ordersJob');
export const ordersRows = place<string[]>('ordersRows');
export const failed = place<Error>('failed');
// ... invoicesJob, invoicesRows, reports, errors

// Take two connections and start both queries.
const start = Transition.builder('start')
  .inputs(one(requests), exactly(2, pool))
  .outputs(and(outPlace(ordersJob), outPlace(invoicesJob)))
  .action(async (ctx) => {
    const [a, b] = ctx.inputs(pool);
    ctx.output(ordersJob, a!);
    ctx.output(invoicesJob, b!);
  })
  .build();
```

Each query is a transition. `xor` means the action writes to exactly one of the branches:

`finish` joins the two row sets into a report, and `fail` turns a failed query into an error. After `start` fires,
both queries are enabled and their promises run at the same time.

### Running it

<Short>One call, 3 ms: a 4-step trace ends with one connection in the pool and one report that can never start.</Short>

The check is a call in a test. `quiescentCount([pool], 2, 2)` says: in every state where nothing can fire, the pool
holds exactly two tokens.

```ts
// report.libpetri.test.ts (shortened)
const result = await SmtVerifier.forNet(reportNet(db))
  .initialMarking((m) => m.tokens(requests, 2).tokens(pool, 2))
  .property(quiescentCount([pool], 2, 2))
  .verify();

result.verdict;                   // { type: 'violated' }
result.counterexampleTransitions; // [ 'start', 'queryInvoices', 'queryOrders', 'fail' ]
```

The trace, one marking per step:

```text
{pool:2, requests:2}
{invoicesJob:1, ordersJob:1, requests:1}
{invoicesRows:1, ordersJob:1, pool:1, requests:1}
{failed:1, invoicesRows:1, pool:1, requests:1}
{errors:1, invoicesRows:1, pool:1, requests:1}
```

The last state is stuck: the second request needs two connections and the pool has one. The net has 48 reachable
states, so libpetri decided it by walking all of them, with no solver: "sound AND complete: a `violated` is a real
firing sequence". With enumeration turned off (`.enumerationMaxClasses(0)`), Z3 finds the same trace in 35 ms.

The test also runs the real net, with a database whose invoices query throws. It ends the same way the trace does:

```ts
const result = await new BitmapNetExecutor(reportNet(failingDb), initialTokens).run();
result.tokenCount(pool);     // 1
result.tokenCount(requests); // 1, never started
```

### Fixing the bug

<Short>Give the connection back on both branches. Proven in 4 ms, and the report names the invariant "every connection is in the pool or in a job".</Short>

The same check now returns `proven`. On the Z3 route, the report shows why:

```text
Phase 3: Computing P-invariants...
  Found: 2 P-invariant(s)
  Structurally bounded: YES
  errors + failed + invoicesJob + invoicesRows + ordersJob + ordersRows + 2*reports + 2*requests = 4
  invoicesJob + ordersJob + pool = 2
...
PROVEN (state equation): Quiescent count: exactly 2 across {pool}
```

`invoicesJob + ordersJob + pool = 2` is the rule in one line: every connection is either in the pool or held by a
running query. In the buggy net the same line had `failed` and `errors` in it, so a connection could end up there.

## Project layout and CI

<Short>The net is the code. Commit it and the test; CI runs Vitest. Install z3 in CI once nets grow past enumeration.</Short>

```text
./
├── .github/workflows/ci.yml
├── report.ts                 the net: places, transitions, actions
└── report.libpetri.test.ts   runs the net and checks it
```

Nothing is generated. The test checks the net that runs in production, so there is no model to drift from the code.

    node-version: 22

- run: npm test

What fails when:

- **A connection can be lost, or a request can wait forever:** the verification test, with the firing sequence.
- **z3 is missing on a net too big to enumerate:** the verdict is `unknown`, with a reason naming the command. Check
  for `proven`, not for "not violated".
- **An action throws instead of writing an output:** the run test. The checker does not look inside actions.

## Making changes

<Short>Change the net, run the test, commit.</Short>

1. Change the net: a new place, arc or transition.
2. If an action changes, check it still writes to the outputs its arcs declare. The checker trusts the arcs.
3. Add a property for any new rule: a bound, a mutual exclusion, a count at rest.
4. Run `npm test`.

## Strengths

- **The net is the program.** The checked net is the one that runs, so a proof is about the real control flow, not a
  copy of it.
- **Resources are visible.** A pool, a budget or a permit is a place with tokens. Leaks and waits that never end
  become properties you can check.
- **Proofs come with a reason.** A proven result can name the invariant, like "every connection is in the pool or in
  a job".
- **Small nets need no solver.** Under the enumeration limit the checker walks every state and gives real traces.
- **Used in production.** It runs the author's production commerce assistant at Otto.
- **Well checked itself.** The same spec is implemented in Java, TypeScript and Rust, each with conformance tests. Lean
  proofs cover how the checker's abstraction relates to the runtime.

## Limitations

- **You write the program as a net.** Existing `async` code has to be rewritten as places and transitions. That is a
  bigger change than adding a spec next to the code.
- **Actions are trusted.** The checker reads arcs, not the code inside actions. An action that skips an output it
  declares is caught only by running it.
- **Values are not checked.** The checker counts tokens and ignores their values and timing. A proof without timing
  holds with timing, but a counterexample can be one that timing rules out.
- **A new way of thinking.** Places, arcs, inhibitors and XOR outputs take time to learn if you have not used Petri
  nets.
- **Large nets need z3** installed on the machine and in CI.
