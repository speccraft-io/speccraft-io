[TLA+](https://lamport.azurewebsites.net/tla/tla.html) is a language for describing a system as state and the steps
that change it, written by Leslie Lamport. AWS, Microsoft and MongoDB use it on their distributed systems. TLA+ is the
language. The checking is done by separate tools, and there are two main ones:

- **TLC**, the original model checker. It walks every reachable state of the spec. It also checks liveness: "this
  always ends", not only "this never breaks".
- **Apalache**, a symbolic checker built on the Z3 solver. It checks every run up to a set number of steps, and handles
  large ranges of values without listing each state. It needs type annotations.

One `.tla` file works with both, which is why this is one page and not three. [Quint](/tools/quint) is a friendlier
language that compiles to TLA+ and runs these same two checkers underneath. This page uses TLA+ directly.

TLA+ describes a system as state, steps and "must never happen" rules, checked in every order. It has its own
language and checks the spec, not the real code. For tools that do the same kind of checking with the model written
in TypeScript, see [TypeScript tools](/ts-tools); for the wider field, see [Non-TypeScript tools](/tools/non-ts-tools).

<Short>Write the spec, let TLC find the order that breaks the key for good, then replay every behavior of the spec against the real TS code.</Short>

<Full>

## A separate spec, on purpose

TLA+ asks for a second, much smaller description of the system in a `.tla` file. You do not annotate your TS code.
That is extra work, and it pays back in three ways:

- Isolation. The spec has no framework, no network, no `async`. Only the state and the steps that matter for the rule.
  Each `await` in the real code becomes a point where the spec can switch to another step.
- Freedom. You choose what to leave out and how coarse the steps are. You can try a different design in minutes and
  check it before anyone changes production code.
- A thinking tool. To write the spec you have to name every state, every step, every "must never happen" and every
  "must eventually happen". Many design bugs show up while writing it, before TLC runs.

The cost is a second artifact to keep in step with the code. The rest of this page shows how to do that with a replay
test in vitest.

</Full>

## Why you would want this

<Short>The test passes, but one failed call leaves its rejected promise in the map, and that key fails forever.</Short>

When many callers ask for the same thing at once, only one call should run, and the others should share it. This is
called single-flight, or request coalescing:

```ts
// src/single-flight.ts
// Callers that ask for the same key while fn() runs share one call.
export function singleFlight<T>() {
  const inflight = new Map<string, Promise<T>>();
  return (key: string, fn: () => Promise<T>) => {
    const running = inflight.get(key);
    if (running) return running;
    const p = fn().then((v) => {
      inflight.delete(key);
      return v;
    });
    inflight.set(key, p);
    return p;
  };
}
```

```ts
// src/single-flight.test.ts
test('five callers at once share one call', async () => {
  const flight = singleFlight<string>();
  let calls = 0;
  const fn = async () => {
    calls++;
    return 'v';
  };
  await Promise.all([1, 2, 3, 4, 5].map(() => flight('u1', fn)));
  expect(calls).toBe(1);
});
```

The test passes, and `fn` never fails in it. In production, the call times out once. The promise in the map is now
rejected, and only the success path removes it. Every later caller for that key finds it and gets the old error at
once, without calling `fn` again, until the process restarts. TLC tries every order, including the ones where `fn`
fails.

## When TLA+ fits

- Several actors change shared state: callers, handlers, timers, retries, queues, locks, leader election, sagas.
- The bug you fear is about order: "what if a caller arrives after the call failed?"
- The rule can be said as "this must never happen" or "this must always happen in the end" (every caller gets a
  value). TLC checks both kinds.

TLA+ is not the tool for proving one function's math right for every input. See the [Lean](/tools/lean) and
[Dafny](/tools/dafny) pages for that.

</Full>

## Install

<Short>One jar and Java 11 or newer. Apalache is a separate download.</Short>

TLC ships in one jar. It needs Java 11 or newer:

```sh
curl -LO https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar
java -jar tla2tools.jar Spec.tla      # runs TLC on Spec.tla with the settings in Spec.cfg
```

The jar also has SANY, the TLA+ parser, and the PlusCal translator. For the editor, install the "TLA+" extension in
VS Code: it highlights and parses specs and runs TLC from the editor.

[Apalache](https://github.com/apalache-mc/apalache) is a separate download: unpack `apalache.tgz` from its GitHub
releases and put `bin/apalache-mc` on your `PATH`. It needs Java 17 or newer. If you already use Quint, `quint verify`
has downloaded a copy into `~/.quint`.

## Step 1: describe the system as state and steps (use AI)

<Short>Variables are the state; each action says when it can happen and what the variables become.</Short>

A TLA+ spec has variables (the state) and actions (the steps that change it). An action is a list of conditions joined
by `/\` (and). A line without `'` is a condition: if it is false, the action cannot happen now. `x'` means "the value
of `x` after this step". Every action must say what every variable becomes, which is what `UNCHANGED` is for.

```text
---- MODULE SingleFlight ----
\* Two callers ask for the same key. The first one starts fn(),
\* the other one shares its promise while it runs.

Callers == {"a", "b"}

VARIABLES entry, pc

vars == <<entry, pc>>

Init ==
    /\ entry = "none"
    /\ pc = [c \in Callers |-> "idle"]

\* A caller asks: it shares the promise in the map, or starts fn() and puts it there.
Call(c) ==
    /\ pc[c] = "idle"
    /\ pc' = [pc EXCEPT ![c] = IF entry = "failed" THEN "failed" ELSE "waiting"]
    /\ entry' = IF entry = "none" THEN "running" ELSE entry

\* fn() resolves: the entry is removed, and every waiting caller gets the value.
Resolve ==
    /\ entry = "running"
    /\ entry' = "none"
    /\ pc' = [c \in Callers |-> IF pc[c] = "waiting" THEN "done" ELSE pc[c]]

\* fn() rejects: every waiting caller gets the error, and the entry stays.
Reject ==
    /\ entry = "running"
    /\ entry' = "failed"
    /\ pc' = [c \in Callers |-> IF pc[c] = "waiting" THEN "failed" ELSE pc[c]]

\* A caller got an error and tries again.
Retry(c) ==
    /\ pc[c] = "failed"
    /\ pc' = [pc EXCEPT ![c] = "idle"]
    /\ UNCHANGED entry

Next == Resolve \/ Reject \/ \E c \in Callers : Call(c) \/ Retry(c)

\* Callers call and retry. fn() may reject, but not every time.
Spec ==
    /\ Init /\ [][Next]_vars
    /\ SF_vars(Resolve)
    /\ \A c \in Callers : WF_vars(Call(c)) /\ WF_vars(Retry(c))

\* Every caller gets a value in the end.
EveryoneGetsIt == \A c \in Callers : <>(pc[c] = "done")

\* No failed call is left in the map.
NoFailedEntry == entry /= "failed"
====
```

And the config file TLC reads next to it:

```text
\* spec/SingleFlight.cfg
SPECIFICATION Spec
PROPERTY EveryoneGetsIt
```

How to read it:

- Two variables: `entry` is the map entry for one key (`"none"`, `"running"` or `"failed"`), and `pc` is where each
  caller is, like a program counter.
- Two callers, `"a"` and `"b"`, are enough. `[c \in Callers |-> "idle"]` is a map, like `Record<string, string>`.
  `pc[c]` reads it, `[pc EXCEPT ![c] = "done"]` returns an updated copy.
- `Call(c)` has a parameter: there is one for each caller. `Resolve` and `Reject` are the two ways `fn()` can end.
  `Retry` is a caller asking again after an error.
- `Next` says what can happen next: any step whose conditions hold. TLC tries each one.
- `Spec` is the whole system: start in `Init`, then take `Next` steps. `WF` and `SF` are fairness: callers do call
  and retry, and `fn()` may reject, but not every time. `SF` (strong fairness) is what says "not every time".
- `EveryoneGetsIt` is a liveness property: `<>` means "at some point". It says every caller gets a value in the end.

## Step 2: let TLC find the bad order

<Short>TLC finds a run where no caller ever gets a value again, in under a second.</Short>

`-deadlock` turns off TLC's deadlock check, since a run where both callers have a value is supposed to stop:

```text
$ java -jar tla2tools.jar -deadlock spec/SingleFlight.tla
Checking 2 branches of temporal properties for the complete state space with 34 total distinct states
Error: Temporal properties were violated.

Error: The following behavior constitutes a counter-example:

State 1: <Initial predicate>
/\ pc = [a |-> "idle", b |-> "idle"]
/\ entry = "none"

State 2: <Call line 17, col 5 to line 19, col 59 of module SingleFlight>
/\ pc = [a |-> "idle", b |-> "waiting"]
/\ entry = "running"

State 3: <Reject line 29, col 5 to line 31, col 78 of module SingleFlight>
/\ pc = [a |-> "idle", b |-> "failed"]
/\ entry = "failed"

State 4: <Call line 17, col 5 to line 19, col 59 of module SingleFlight>
/\ pc = [a |-> "failed", b |-> "failed"]
/\ entry = "failed"

State 5: <Retry line 35, col 5 to line 37, col 22 of module SingleFlight>
/\ pc = [a |-> "failed", b |-> "idle"]
/\ entry = "failed"

State 6: <Call line 17, col 5 to line 19, col 59 of module SingleFlight>
/\ pc = [a |-> "failed", b |-> "failed"]
/\ entry = "failed"

Back to state 3: <Retry line 35, col 5 to line 37, col 22 of module SingleFlight>
```

Read it as a timeline:

1. Caller `b` calls, and `fn()` starts.
2. `fn()` rejects. `b` gets the error, and the failed entry stays in the map.
3. Caller `a` calls, finds the failed entry, and gets the old error at once.
4. `b` retries and gets the same error. `Back to state 3` means this loops forever: `fn()` is never called again.

No test with the word "race" in its name would look for this, and an invariant cannot say it either: every single
state here looks fine. Only the whole run is wrong. That is what liveness properties are for.

## Step 3: fix it

<Short>Remove the entry when the call ends either way. The property holds.</Short>

The entry must go when the call settles, whether it resolves or rejects. In the TS code that is `.finally()`. In the
spec, `Reject` now sets the entry back to `"none"`, like `Resolve`:

## Step 4: the same spec in Apalache

<Short>Add a type comment to each variable; Apalache checks the "never" rule with Z3.</Short>

Apalache reads the same file. It needs one type comment per variable, and ignores them otherwise, so TLC still runs
the annotated file:

```text
VARIABLES
    \* @type: Str;
    entry,
    \* @type: Str -> Str;
    pc
```

Apalache checks "must never happen" rules; it has no fairness, so it cannot check `EveryoneGetsIt`. The same bug as a
"never" rule is the last line of the spec: `NoFailedEntry`, no failed call is left in the map. On the Step 1 spec:

```text
$ apalache-mc check --no-deadlock --inv=NoFailedEntry --length=10 spec/SingleFlight.tla
State 2: state invariant 0 violated.
Found 1 error(s)
The outcome is: Error
Total time: 1.256 sec
```

On the fixed spec:

```text
$ apalache-mc check --no-deadlock --inv=NoFailedEntry --length=10 spec/SingleFlight.tla
The outcome is: NoError
Checker reports no error up to computation length 10
Total time: 1.360 sec
```

Callers can retry forever, so runs of this spec never stop. Apalache checked every run up to 10 steps; TLC checked
every state, which covers runs of any length. Apalache also writes a counterexample as `violation1.itf.json` in
`_apalache-out/`, the same trace format Quint uses.

Which checker to use:

| | TLC | Apalache |
|---|---|---|
| How | Lists every reachable state | Turns runs into Z3 formulas |
| Covers | Every state, however many steps | Every run up to `--length` steps |
| Liveness (`<>`, fairness) | Yes | Limited |
| Big value ranges (amounts, counters) | Slow: each value is a state | Fast: a range is one formula |
| Needs | Java 11+, one jar | Java 17+, type comments |

Start with TLC. Reach for Apalache when a variable holds amounts or large numbers and TLC's state count blows up.

## Step 5: replay every behavior against the real TS code (use AI)

<Short>TLC writes its whole state graph; vitest walks every path in it against the real function.</Short>

The spec is right. Nothing yet says the TS code behaves like the spec. TLC can write the whole state graph it
explored, with each edge labeled by its action:

```sh
java -jar tla2tools.jar -deadlock -dump dot,actionlabels spec/out/graph spec/SingleFlight.tla
```

That writes `spec/out/graph.dot`: one node per state, one edge per step. The spec is small, so the test can walk every
path from the first state until it stops or comes back to a state it has already been in. That is every behavior of
the spec up to its first loop, not a sample. For each path, it drives the real `singleFlight` with an `fn` whose calls
wait until the path says how they end:

```ts
// src/single-flight.tla.test.ts
import { readFileSync } from 'node:fs';
import { expect, test } from 'vitest';
import { singleFlight } from './single-flight';

// TLC's state graph (-dump dot,actionlabels): one node per state, one edge per step.
type Status = 'idle' | 'waiting' | 'done' | 'failed';
interface State {
  running: boolean;
  pc: Record<string, Status>;
}
interface Edge {
  to: string;
  action: string;
}

function readGraph(file: URL) {
  const states = new Map<string, State>();
  const edges = new Map<string, Edge[]>();
  let init = '';
  for (const line of readFileSync(file, 'utf8').split('\n')) {
    const node = line.match(/^(-?\d+) \[label="(.*)"(,style = filled)?\]/);
    if (node) {
      const pc = Object.fromEntries(
        [...node[2].matchAll(/(\w+) \|-> \\"(\w+)\\"/g)].map((m) => [m[1], m[2] as Status]),
      );
      states.set(node[1], { running: node[2].includes('entry = \\"running\\"'), pc });
      if (node[3]) init = node[1];
    }
    const edge = line.match(/^(-?\d+) -> (-?\d+) \[label="(\w+)"/);
    if (edge && edge[1] !== edge[2]) {
      edges.set(edge[1], [...(edges.get(edge[1]) ?? []), { to: edge[2], action: edge[3] }]);
    }
  }
  return { states, edges, init };
}

// Every behavior of the model: each path from the initial state until it stops,
// or until it comes back to a state it has already been in.
function allPaths(graph: ReturnType<typeof readGraph>): Edge[][] {
  const walk = (from: string, seen: Set<string>): Edge[][] => {
    const next = graph.edges.get(from) ?? [];
    if (next.length === 0) return [[]];
    return next.flatMap((e) =>
      seen.has(e.to) ? [[e]] : walk(e.to, new Set([...seen, e.to])).map((rest) => [e, ...rest]),
    );
  };
  return walk(graph.init, new Set([graph.init]));
}

// Each fn() call waits until the replay says how it ends.
function world() {
  const calls: { ok: () => void; fail: () => void }[] = [];
  const fn = () =>
    new Promise<string>((resolve, reject) => {
      calls.push({ ok: () => resolve('v'), fail: () => reject(new Error('down')) });
    });
  const flight = singleFlight<string>();
  const status: Record<string, Status> = { a: 'idle', b: 'idle' };
  const call = (c: string) => {
    status[c] = 'waiting';
    flight('k', fn).then(
      () => (status[c] = 'done'),
      () => (status[c] = 'failed'),
    );
  };
  const finish = (how: 'ok' | 'fail') => {
    expect(calls.length, 'the model says fn() ends here, but no call is running').toBe(1);
    calls.pop()![how]();
  };
  return { calls, status, call, finish };
}

const settle = () => new Promise((resolve) => setTimeout(resolve, 0));

// The edge label has no caller: it is the one whose status changes.
const graph = readGraph(new URL('../spec/out/graph.dot', import.meta.url));
const steps = (path: Edge[]) => {
  let from = graph.init;
  return path.map(({ to, action }) => {
    const [a, b] = [graph.states.get(from)!, graph.states.get(to)!];
    const who = Object.keys(b.pc).filter((c) => a.pc[c] !== b.pc[c]);
    from = to;
    const name = action === 'Call' || action === 'Retry' ? `${action}(${who[0]})` : action;
    return { to, action, who: who[0], name };
  });
};
const paths = allPaths(graph)
  .map(steps)
  .map((path) => [path.map((s) => s.name).join(' → '), path] as const);

test.each(paths)('%s', async (_name, path) => {
  const { calls, status, call, finish } = world();

  for (const { to, action, who, name } of path) {
    if (action === 'Call') call(who);
    else if (action === 'Resolve') finish('ok');
    else if (action === 'Reject') finish('fail');
    else if (action === 'Retry') status[who] = 'idle';
    else throw new Error(`no mapping for action ${action}`);
    await settle();

    const model = graph.states.get(to)!;
    expect({ step: name, running: calls.length === 1, ...status }).toEqual({
      step: name,
      running: model.running,
      ...model.pc,
    });
  }
});
```

What it does for each step of a path:

- The edge label says which action ran, but not for which caller. The test finds the caller by comparing the two
  states: the one whose `pc` changed.
- `Call` calls the real function. `Resolve` and `Reject` make the waiting `fn()` call resolve or reject. If no call is
  waiting, the code and the spec disagree, and the test says so.
- After each step, whether `fn()` is running and each caller's status must match the spec.
- Each path is its own test, named by its steps, so a failure reads as the exact order that differs.

Replay the fixed spec against the original function, the way it goes when you fix the spec first:

```text
$ npx vitest run src/single-flight.tla.test.ts
 ❯ src/single-flight.tla.test.ts (88 tests | 76 failed)
   × Call(a) → Reject → Call(b) → Reject → Retry(b)
   ...

AssertionError: expected { step: 'Call(b)', …(3) } to deeply equal { Object (step, running, ...) }

  {
    "a": "failed",
-   "b": "waiting",
-   "running": true,
+   "b": "failed",
+   "running": false,
    "step": "Call(b)",
  }
```

After `a`'s call rejected, the spec says `b`'s call starts a new `fn()`. The original code gives `b` the old error
instead. With the fix from Step 3, all 88 behaviors pass.

One thing the replay cannot do: the original function against the Step 1 spec passes all 38 behaviors. The code does
what that spec says, step by step. The stuck key breaks no step and no state, only the run as a whole. TLC's
`EveryoneGetsIt` check on the spec is what catches it.

## Project layout and CI

<Short>One script checks the spec and writes the graph; the replay always reads a fresh one.</Short>

One repo. The spec sits in its own folder. The graph is written from it on every test run and never committed:

```text
./
├── .github/workflows/ci.yml
├── spec/
│   ├── SingleFlight.tla            the spec: state, steps and EveryoneGetsIt
│   ├── SingleFlight.cfg            which spec and properties TLC checks
│   └── out/                        graph and TLC's working files, git-ignored
├── src/
│   ├── single-flight.ts            the real function
│   ├── single-flight.test.ts       normal unit tests
│   └── single-flight.tla.test.ts   replays spec/out/graph.dot against single-flight.ts
├── tools/tla2tools.jar             downloaded, git-ignored
├── .gitignore                      node_modules, spec/out/, tools/
├── package.json
└── tsconfig.json
```

Scripts in `package.json`:

```json
"scripts": {
  "tla:install": "mkdir -p tools && curl -sLo tools/tla2tools.jar https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar",
  "tla:check": "java -jar tools/tla2tools.jar -deadlock -cleanup -metadir spec/out/meta -dump dot,actionlabels spec/out/graph spec/SingleFlight.tla",
  "pretest": "npm run tla:check",
  "typecheck": "tsc",
  "test": "vitest run"
}
```

- `tla:install` pins the TLC version in one place.
- `tla:check` checks the property and writes the graph in one run. `-metadir` keeps TLC's working files in
  `spec/out/` instead of a `states/` folder in the repo root.
- `pretest` runs before `npm test`, so the replay always walks the graph of the current spec. If the spec breaks a
  property, TLC exits with an error and the tests do not run.

TLC and the replay both need Java, so CI is one job:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: 21
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - uses: actions/cache@v6
        with:
          path: tools
          key: tla-${{ hashFiles('package.json') }}
      - run: npm ci
      - run: test -f tools/tla2tools.jar || npm run tla:install
      - run: npm run typecheck
      - name: Check the spec, then replay every behavior against the real function
        run: npm test
```

What fails when:

| Change | Where CI fails |
|---|---|
| A spec change breaks `EveryoneGetsIt` | `npm test`, in `pretest`: TLC prints the counterexample |
| The function changes and no longer follows the spec | `single-flight.tla.test.ts`: the path and step where the code and the spec differ |
| The spec changes, the function does not | `single-flight.tla.test.ts`: the new paths no longer match the old function |
| The spec gets a new action | `single-flight.tla.test.ts`: `no mapping for action ...` |

## Making changes

<Short>Change the spec first and check it, then change the code until the replay passes.</Short>

Changing the flow (for example, a caller can cancel while it waits):

1. Change the spec first: a new action, the variables it touches, and a rule if there is a new "must never happen" or
   "must always happen".
2. Run `npm run tla:check` until TLC passes.
3. Change the function. Map the new action in `single-flight.tla.test.ts`.
4. Run `npm test` until the replay passes. Commit the spec, the function and the replay test together.

When the graph grows: walking every path works while the spec is small. Past a few thousand paths, replay a sample.
TLC's `-simulate` mode writes random runs, and Apalache and Quint write traces as ITF JSON (see the
[Quint page](/tools/quint) for a replay built on those).

Reviewing a pull request: read the spec diff first. A new `await` in the code with no new step in the spec means the
spec no longer splits the code where it can interleave. That is the one mistake the replay cannot catch, because the
replay follows the spec's steps.

## What you get, and what you do not

You get:

- Every order of steps checked, in the spec, in under a second at this size.
- Liveness: "every caller gets a value in the end" is checked, not only "nothing bad happens". That is how the stuck
  key was found.
- A shortest failing order, as a readable trace, instead of a bug that shows up once a month after a timeout.
- A fix you can check before you write it in TS.
- Every behavior of a small spec, up to its first loop, replayed against the real code.

You do not get:

- A proof about the TS code. TLC checks the spec. The replay checks the code on the spec's behaviors, and it cannot
  check liveness in the code.
- A free spec. You choose where the steps split. If you merge steps that the real code keeps apart, the spec hides
  the bug.
- Anything the spec leaves out. Here: more than one key, and more than one process. Neither is in the spec, so TLC
  says nothing about them.
- A familiar syntax. `/\`, `'`, `EXCEPT` and `<>` take a day to get used to. A coding agent writes them well from a
  TS function, and [Quint](/tools/quint) exists for teams who want the same checkers with a friendlier language.

</Full>

## How to start in your own project

1. Pick one flow where order matters: shared calls, a signal and a timer, a retry loop, a lock, a saga.
2. Write the rules as "this must never happen" and "this must always happen in the end".
3. List the variables, including the ones outside your code: calls in flight, what each caller has seen.
4. Make one action per step between two `await`s in the real code, and one action per way a call can end.
5. Say which steps are fair (callers call, calls return) and which are not (a call may fail).
6. Run TLC with 2 or 3 actors, then dump the graph and replay it against the real code with controlled fakes.
