[TLA+](https://lamport.azurewebsites.net/tla/tla.html) is a language for describing a system as state and the steps
that change it, written by Leslie Lamport. AWS, Microsoft and MongoDB use it on their distributed systems. TLA+ is the
language. The checking is done by separate tools, and there are two main ones:

- **TLC**, the original model checker. It walks every reachable state of the spec. It also checks liveness: "this
  always ends", not only "this never breaks".
- **Apalache**, a symbolic checker built on the Z3 solver. It checks every run up to a set number of steps, and handles
  large ranges of values without listing each state. It needs type annotations.

One `.tla` file works with both, which is why this is one page and not three. [Quint](/tools/quint) is a friendlier
language that compiles to TLA+ and runs these same two checkers underneath. This page uses TLA+ directly.

TLA+ describes a system as state, steps and "must never happen" rules, checked in every order. It has its own
language and checks the spec, not the real code. For tools that do the same kind of checking with the model written
in TypeScript, see [TypeScript tools](/ts-tools); for the wider field, see [Non-TypeScript tools](/tools/non-ts-tools).

<Short>Write the spec, let TLC find the bad order and the stuck state, then replay every behavior of the spec against the real TS code.</Short>

<Full>

## A separate spec, on purpose

TLA+ asks for a second, much smaller description of the system in a `.tla` file. You do not annotate your TS code.
That is extra work, and it pays back in three ways:

- Isolation. The spec has no framework, no card network SDK, no `async`. Only the state and the steps that matter for
  the rule. Each `await` in the real code becomes a point where the spec can switch to another step.
- Freedom. You choose what to leave out and how coarse the steps are. You can try a different design in minutes and
  check it before anyone changes production code.
- A thinking tool. To write the spec you have to name every state, every step, every "must never happen" and every
  "must eventually happen". Many design bugs show up while writing it, before TLC runs.

The cost is a second artifact to keep in step with the code. The rest of this page shows how to do that with a replay
test in vitest.

</Full>

## Why you would want this

<Short>Both tests pass, but an approval that lands while the timer is firing takes the money and gives the hold back.</Short>

An order puts a hold on the customer's card. A manager can approve the order, which captures the money. If nobody
approves within 24 hours, a timer releases the hold. Whichever comes first wins, and a flag stops the other one:

```ts
// src/payment-hold.ts
export interface Deps {
  capture(orderId: string): Promise<void>; // take the held money
  release(orderId: string): Promise<void>; // give the hold back to the customer
}

// One per order. approve() runs when a manager approves the order,
// expire() when the 24h timer fires. Whichever comes first wins.
export class PaymentHold {
  private settled = false;

  constructor(
    private orderId: string,
    private deps: Deps,
  ) {}

  async approve(): Promise<void> {
    if (this.settled) return;
    await this.deps.capture(this.orderId);
    this.settled = true;
  }

  async expire(): Promise<void> {
    if (this.settled) return;
    await this.deps.release(this.orderId);
    this.settled = true;
  }
}
```

```ts
// src/payment-hold.test.ts
test('approval captures, and the timer then does nothing', async () => {
  const { bank, deps } = fakeDeps();
  const hold = new PaymentHold('o1', deps);
  await hold.approve();
  await hold.expire();
  expect(bank).toEqual({ captured: 1, released: 0 });
});

test('the timer releases, and a late approval does nothing', async () => {
  const { bank, deps } = fakeDeps();
  const hold = new PaymentHold('o1', deps);
  await hold.expire();
  await hold.approve();
  expect(bank).toEqual({ captured: 0, released: 1 });
});
```

Both tests pass. Each one lets the first handler finish before the second one starts. In production, the manager
clicks "approve" at 23:59:59, the card network takes two seconds to answer, and the timer fires in between. This is
the shape of bug durable workflows are full of: a signal handler and a timer sharing state across an `await`. TLC
tries every order.

<Full>

## When TLA+ fits

- Several actors change shared state: handlers, timers, retries, queues, locks, leader election, sagas.
- The bug you fear is about order: "what if the timer fires while the capture is in flight?"
- The rule can be said as "this must never happen" (never capture and release) or "this must always happen in the
  end" (every hold is settled). TLC checks both kinds.

TLA+ is not the tool for proving one function's math right for every input. See the [Lean](/tools/lean) and
[Dafny](/tools/dafny) pages for that.

</Full>

## Install

<Short>One jar and Java 11 or newer. Apalache is a separate download.</Short>

TLC ships in one jar. It needs Java 11 or newer:

```sh
curl -LO https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar
java -jar tla2tools.jar Spec.tla      # runs TLC on Spec.tla with the settings in Spec.cfg
```

The jar also has SANY, the TLA+ parser, and the PlusCal translator. For the editor, install the "TLA+" extension in
VS Code: it highlights and parses specs and runs TLC from the editor.

[Apalache](https://github.com/apalache-mc/apalache) is a separate download: unpack `apalache.tgz` from its GitHub
releases and put `bin/apalache-mc` on your `PATH`. It needs Java 17 or newer. If you already use Quint, `quint verify`
has downloaded a copy into `~/.quint`.

## Step 1: describe the system as state and steps (use AI)

<Short>Variables are the state; each action says when it can happen and what the variables become.</Short>

A TLA+ spec has variables (the state) and actions (the steps that change it). An action is a list of conditions joined
by `/\` (and). A line without `'` is a condition: if it is false, the action cannot happen now. `x'` means "the value
of `x` after this step". Every action must say what every variable becomes, which is what `UNCHANGED` is for.

```text
---- MODULE PaymentHold ----
\* A card hold on one order. A manager may approve it (capture the money),
\* and a 24h timer releases it back to the customer. Both handlers share one flag.

VARIABLES settled, captured, released, pc

vars == <<settled, captured, released, pc>>

Init ==
    /\ settled = FALSE
    /\ captured = FALSE
    /\ released = FALSE
    /\ pc = [h \in {"approve", "expire"} |-> "idle"]

\* approve() starts: reads the flag, then awaits capture() if the hold is open.
StartApprove ==
    /\ pc["approve"] = "idle"
    /\ pc' = [pc EXCEPT !["approve"] = IF settled THEN "done" ELSE "capturing"]
    /\ UNCHANGED <<settled, captured, released>>

\* capture() returns, and approve() sets the flag.
CaptureOk ==
    /\ pc["approve"] = "capturing"
    /\ captured' = TRUE
    /\ settled' = TRUE
    /\ pc' = [pc EXCEPT !["approve"] = "done"]
    /\ UNCHANGED released

\* capture() throws (card declined, bank timeout). approve() rethrows, the flag stays as it was.
CaptureFails ==
    /\ pc["approve"] = "capturing"
    /\ pc' = [pc EXCEPT !["approve"] = "done"]
    /\ UNCHANGED <<settled, captured, released>>

\* The 24h timer fires: expire() reads the flag, then awaits release() if the hold is open.
StartExpire ==
    /\ pc["expire"] = "idle"
    /\ pc' = [pc EXCEPT !["expire"] = IF settled THEN "done" ELSE "releasing"]
    /\ UNCHANGED <<settled, captured, released>>

\* release() returns, and expire() sets the flag.
ReleaseOk ==
    /\ pc["expire"] = "releasing"
    /\ released' = TRUE
    /\ settled' = TRUE
    /\ pc' = [pc EXCEPT !["expire"] = "done"]
    /\ UNCHANGED captured

Next == StartApprove \/ CaptureOk \/ CaptureFails \/ StartExpire \/ ReleaseOk

\* The timer always fires and awaited calls always return; the manager may never approve.
Spec ==
    /\ Init /\ [][Next]_vars
    /\ WF_vars(StartExpire) /\ WF_vars(ReleaseOk) /\ WF_vars(CaptureOk \/ CaptureFails)

\* Never take the money and also give the hold back.
NotBoth == ~(captured /\ released)

\* Every hold ends: the money is either taken or given back.
Settles == <>(captured \/ released)
====
```

And the config file TLC reads next to it:

```text
\* spec/PaymentHold.cfg
SPECIFICATION Spec
INVARIANT NotBoth
PROPERTY Settles
```

How to read it:

- The variables are the whole world, not just the class: `settled` (the flag), `captured` and `released` (what the
  card network did), and `pc` (where each handler is, like a program counter).
- `[h \in {"approve", "expire"} |-> "idle"]` is a map, like `Record<string, string>`. `pc["approve"]` reads it,
  `[pc EXCEPT !["approve"] = "done"]` returns an updated copy.
- Each handler is split into steps exactly where the TS code has an `await`: `StartApprove` (the flag check and the
  call to `capture`), then `CaptureOk` or `CaptureFails` (how the call ends). The same for `expire`.
- `Next` says what can happen next: any of the five steps whose conditions hold. TLC tries each one.
- `Spec` is the whole system: start in `Init`, then take `Next` steps. The `WF_vars(...)` parts are fairness: a step
  that stays possible will happen in the end. The timer does fire and the card network does answer, but nothing forces
  the manager to approve, so `StartApprove` has no fairness.
- `NotBoth` is an invariant: true in every state. `Settles` is a liveness property: `<>` means "at some point". It says
  every run reaches a state where the money was taken or given back.

## Step 2: let TLC find the bad order

<Short>TLC finds the capture-and-release in under a second, in 13 states.</Short>

`-deadlock` turns off TLC's deadlock check, since a hold that is settled is supposed to stop:

```text
$ java -jar tla2tools.jar -deadlock spec/PaymentHold.tla
Error: Invariant NotBoth is violated.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ pc = [approve |-> "idle", expire |-> "idle"]
/\ settled = FALSE
/\ captured = FALSE
/\ released = FALSE

State 2: <StartApprove line 17, col 5 to line 19, col 48 of module PaymentHold>
/\ pc = [approve |-> "capturing", expire |-> "idle"]
...
State 3: <StartExpire line 37, col 5 to line 39, col 48 of module PaymentHold>
/\ pc = [approve |-> "capturing", expire |-> "releasing"]
...
State 4: <CaptureOk line 23, col 5 to line 27, col 25 of module PaymentHold>
/\ pc = [approve |-> "done", expire |-> "releasing"]
/\ settled = TRUE
/\ captured = TRUE
/\ released = FALSE

State 5: <ReleaseOk line 43, col 5 to line 47, col 25 of module PaymentHold>
/\ pc = [approve |-> "done", expire |-> "done"]
/\ settled = TRUE
/\ captured = TRUE
/\ released = TRUE

16 states generated, 13 distinct states found, 2 states left on queue.
Finished in 00s
```

Read it as a timeline:

1. The manager approves. `approve()` reads `settled = false` and calls `capture()`.
2. The timer fires while the capture is in flight. `expire()` also reads `settled = false` and calls `release()`.
3. The capture succeeds: the money is taken.
4. The release succeeds: the hold is given back. The customer paid nothing for an approved order, or the release fails
   against a hold that is already captured, depending on the bank.

The whole spec has 13 distinct states. TLC checks them in breadth-first order, so the trace it prints is a shortest
one. Most races need only two or three actors to show up.

...
State 2: <StartApprove line 17, col 5 to line 20, col 39 of module PaymentHold>
/\ pc = [approve |-> "capturing", expire |-> "idle"]
/\ settled = TRUE
...
State 3: <StartExpire line 37, col 5 to line 40, col 39 of module PaymentHold>
/\ pc = [approve |-> "capturing", expire |-> "done"]
...
State 4: <CaptureFails line 31, col 5 to line 33, col 48 of module PaymentHold>
/\ pc = [approve |-> "done", expire |-> "done"]
/\ settled = TRUE

The manager approves and the flag is set. The timer fires, sees the flag and does nothing. Then the card is declined.
Nobody is left to release the hold, and `Stuttering` means the system stays in that state forever: the customer's
money is held with no order behind it.

Before the fix, a declined capture left the flag down, and the timer released the hold later. The fix traded a race for
a stuck state. No test with the word "race" in its name would look for this, and an invariant cannot say it either:
every single state here is fine. Only the whole run is wrong. That is what liveness properties are for.

## Step 4: fix it properly

<Short>If the capture fails, `approve()` releases the hold itself. Both properties hold.</Short>

Whoever sets the flag owns the hold, so it must settle it. If the capture fails, `approve()` releases the hold before
it rethrows. In the spec, `CaptureFails` now leads to a new `ReleaseAfterFail` step, with fairness like the others:

## Step 5: the same spec in Apalache

<Short>Add a type comment to each variable; Apalache finds the same race with Z3.</Short>

Apalache reads the same file. It needs one type comment per variable, and ignores them otherwise, so TLC still runs
the annotated file:

```text
VARIABLES
    \* @type: Bool;
    settled,
    \* @type: Bool;
    captured,
    \* @type: Bool;
    released,
    \* @type: Str -> Str;
    pc
```

On the Step 1 spec it finds the same four-step race:

```text
$ apalache-mc check --no-deadlock --inv=NotBoth --length=10 spec/PaymentHold.tla
State 4: state invariant 0 violated.
Found 1 error(s)
The outcome is: Error
Total time: 1.503 sec
```

On the fixed spec:

```text
$ apalache-mc check --no-deadlock --inv=NotBoth --length=10 spec/PaymentHold.tla
The outcome is: ExecutionsTooShort
Checker reports no error up to computation length 10
Total time: 1.194 sec
```

`ExecutionsTooShort` means every run of this spec stops before 10 steps, so all of them were checked. Apalache also
writes the counterexample as `violation1.itf.json` in `_apalache-out/`, the same trace format Quint uses.

Which checker to use:

| | TLC | Apalache |
|---|---|---|
| How | Lists every reachable state | Turns runs into Z3 formulas |
| Covers | Every state, however many steps | Every run up to `--length` steps |
| Liveness (`<>`, fairness) | Yes | Limited |
| Big value ranges (amounts, counters) | Slow: each value is a state | Fast: a range is one formula |
| Needs | Java 11+, one jar | Java 17+, type comments |

Start with TLC. Reach for Apalache when a variable holds amounts or large numbers and TLC's state count blows up.

## Step 6: replay every behavior against the real TS code (use AI)

<Short>TLC writes its whole state graph; vitest walks every path in it against the real class.</Short>

The spec is right. Nothing yet says the TS code behaves like the spec. TLC can write the whole state graph it
explored, with each edge labeled by its action:

```sh
java -jar tla2tools.jar -deadlock -dump dot,actionlabels spec/out/graph spec/PaymentHold.tla
```

That writes `spec/out/graph.dot`: one node per state, one edge per step. The spec is small, so the test can walk every
path from the first state to a final one. That is every behavior of the spec, not a sample. For each path, it drives the
real `PaymentHold` with a fake bank whose calls wait until the path says how they end:

```ts
// src/payment-hold.tla.test.ts
import { readFileSync } from 'node:fs';
import { expect, test } from 'vitest';
import { PaymentHold } from './payment-hold';

// TLC's state graph (-dump dot,actionlabels): one node per state, one edge per step.
interface State {
  captured: boolean;
  released: boolean;
}
interface Edge {
  to: string;
  action: string;
}

function readGraph(file: URL) {
  const states = new Map<string, State>();
  const edges = new Map<string, Edge[]>();
  let init = '';
  for (const line of readFileSync(file, 'utf8').split('\n')) {
    const node = line.match(/^(-?\d+) \[label="(.*)"(,style = filled)?\]/);
    if (node) {
      states.set(node[1], {
        captured: node[2].includes('captured = TRUE'),
        released: node[2].includes('released = TRUE'),
      });
      if (node[3]) init = node[1];
    }
    const edge = line.match(/^(-?\d+) -> (-?\d+) \[label="(\w+)"/);
    if (edge && edge[1] !== edge[2]) {
      edges.set(edge[1], [...(edges.get(edge[1]) ?? []), { to: edge[2], action: edge[3] }]);
    }
  }
  return { states, edges, init };
}

// Every behavior of the model: each path from the initial state to a state with no next step.
function allPaths(graph: ReturnType<typeof readGraph>): Edge[][] {
  const walk = (from: string): Edge[][] => {
    const next = graph.edges.get(from) ?? [];
    if (next.length === 0) return [[]];
    return next.flatMap((e) => walk(e.to).map((rest) => [e, ...rest]));
  };
  return walk(graph.init);
}

// Fake bank: each call waits until the replay says how it ends.
function world() {
  const bank = { captured: false, released: false };
  const pending: { kind: 'capture' | 'release'; ok: () => void; fail: () => void }[] = [];
  const call = (kind: 'capture' | 'release') =>
    new Promise<void>((resolve, reject) => {
      pending.push({
        kind,
        ok: () => {
          bank[kind === 'capture' ? 'captured' : 'released'] = true;
          resolve();
        },
        fail: () => reject(new Error(`${kind} failed`)),
      });
    });
  const hold = new PaymentHold('o1', { capture: () => call('capture'), release: () => call('release') });
  const finish = (kind: 'capture' | 'release', how: 'ok' | 'fail') => {
    const i = pending.findIndex((p) => p.kind === kind);
    expect(i, `the model says a ${kind}() call ends here, but the code is not waiting on one`).toBeGreaterThan(-1);
    pending.splice(i, 1)[0][how]();
  };
  return { bank, hold, finish };
}

const settle = () => new Promise((resolve) => setTimeout(resolve, 0));
const ignore = (p: Promise<void>) => p.catch(() => {});

const graph = readGraph(new URL('../spec/out/graph.dot', import.meta.url));
const paths = allPaths(graph).map((path) => [path.map((e) => e.action).join(' → '), path] as const);

test.each(paths)('%s', async (_name, path) => {
  const { bank, hold, finish } = world();

  for (const { to, action } of path) {
    if (action === 'StartApprove') ignore(hold.approve());
    else if (action === 'StartExpire') ignore(hold.expire());
    else if (action === 'CaptureOk') finish('capture', 'ok');
    else if (action === 'CaptureFails') finish('capture', 'fail');
    else if (action === 'ReleaseOk' || action === 'ReleaseAfterFail') finish('release', 'ok');
    else throw new Error(`no mapping for action ${action}`);
    await settle();

    expect({ action, ...bank }).toEqual({ action, ...graph.states.get(to) });
    expect(bank.captured && bank.released, 'captured and released').toBe(false);
  }
});
```

What it does for each step of a path:

- A start step calls the real `approve()` or `expire()`. It runs until it waits on the bank, or returns at once if
  the flag is set.
- An end step makes the waiting `capture()` or `release()` succeed or throw. If the code is not waiting on that call,
  the code and the spec disagree, and the test says so.
- After each step, the fake bank must match the spec's `captured` and `released`, and must never have done both.
- Each path is its own test, named by its steps, so a failure reads as the exact order that breaks.

First, replay the Step 1 spec against the original class. TLC stops at the first violation, so to get the full graph,
run it once with a config that leaves out the `INVARIANT` line:

```text
$ npx vitest run src/payment-hold.tla.test.ts
 ❯ src/payment-hold.tla.test.ts (11 tests | 4 failed)
   × StartApprove → StartExpire → CaptureOk → ReleaseOk
   × StartApprove → StartExpire → ReleaseOk → CaptureOk
   × StartExpire → StartApprove → CaptureOk → ReleaseOk
   × StartExpire → StartApprove → ReleaseOk → CaptureOk

AssertionError: captured and released: expected true to be false
```

The spec has 11 behaviors. The real class followed the spec at every step of all of them, and broke the rule on the 4
where both handlers read the flag before either call returned. The TLC counterexample is now a failing vitest on your
real code.

After Step 4, the fixed class against the fixed spec: 7 behaviors, all pass. To check the replay is not passing by
accident, run the fixed class against the Step 1 graph: 7 of 11 fail with "the model says a release() call ends here,
but the code is not waiting on one", because the fixed `approve()` no longer lets the timer in. The replay notices when
the code and the spec differ, not just when the rule breaks.

One thing the replay cannot do: the Step 3 class against the Step 3 spec passes all 6 behaviors. The stuck hold breaks
no step and no state, only the run as a whole. TLC's `Settles` check on the spec is what catches it.

## Project layout and CI

<Short>One script checks the spec and writes the graph; the replay always reads a fresh one.</Short>

One repo. The spec sits in its own folder. The graph is written from it on every test run and never committed:

```text
./
├── .github/workflows/ci.yml
├── spec/
│   ├── PaymentHold.tla          the spec: state, steps, NotBoth and Settles
│   ├── PaymentHold.cfg          which spec and properties TLC checks
│   └── out/                     graph and TLC's working files, git-ignored
├── src/
│   ├── payment-hold.ts          the real class
│   ├── payment-hold.test.ts     normal unit tests
│   └── payment-hold.tla.test.ts replays spec/out/graph.dot against payment-hold.ts
├── tools/tla2tools.jar          downloaded, git-ignored
├── .gitignore                   node_modules, spec/out/, tools/
├── package.json
└── tsconfig.json
```

Scripts in `package.json`:

```json
"scripts": {
  "tla:install": "mkdir -p tools && curl -sLo tools/tla2tools.jar https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar",
  "tla:check": "java -jar tools/tla2tools.jar -deadlock -cleanup -metadir spec/out/meta -dump dot,actionlabels spec/out/graph spec/PaymentHold.tla",
  "pretest": "npm run tla:check",
  "typecheck": "tsc",
  "test": "vitest run"
}
```

- `tla:install` pins the TLC version in one place.
- `tla:check` checks both properties and writes the graph in one run. `-metadir` keeps TLC's working files in
  `spec/out/` instead of a `states/` folder in the repo root.
- `pretest` runs before `npm test`, so the replay always walks the graph of the current spec. If the spec breaks a
  property, TLC exits with an error and the tests do not run on a half-written graph.

TLC and the replay both need Java, so CI is one job:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: 21
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - uses: actions/cache@v6
        with:
          path: tools
          key: tla-${{ hashFiles('package.json') }}
      - run: npm ci
      - run: test -f tools/tla2tools.jar || npm run tla:install
      - run: npm run typecheck
      - name: Check the spec, then replay every behavior against the real class
        run: npm test
```

What fails when:

| Change | Where CI fails |
|---|---|
| A spec change breaks `NotBoth` or `Settles` | `npm test`, in `pretest`: TLC prints the counterexample |
| The class changes and no longer follows the spec | `payment-hold.tla.test.ts`: the path and step where the code and the spec differ |
| The spec changes, the class does not | `payment-hold.tla.test.ts`: the new paths no longer match the old class |
| The spec gets a new action | `payment-hold.tla.test.ts`: `no mapping for action ...` |

## Making changes

<Short>Change the spec first and check it, then change the code until the replay passes.</Short>

Changing the flow (for example, a manager can reject as well as approve):

1. Change the spec first: a new action, the variables it touches, and a rule if there is a new "must never happen" or
   "must always happen".
2. Run `npm run tla:check` until TLC passes.
3. Change the class. Map the new action in `payment-hold.tla.test.ts` (which method to call, which call to end).
4. Run `npm test` until the replay passes. Commit the spec, the class and the replay test together.

When the graph grows: walking every path works while the spec is small. Past a few thousand paths, replay a sample.
TLC's `-simulate` mode writes random runs, and Apalache and Quint write traces as ITF JSON (see the
[Quint page](/tools/quint) for a replay built on those).

Reviewing a pull request: read the spec diff first. A new `await` in the class with no new step in the spec means the
spec no longer splits the code where it can interleave. That is the one mistake the replay cannot catch, because the
replay follows the spec's steps.

## What you get, and what you do not

You get:

- Every order of steps checked, in the spec, in under a second at this size.
- Liveness: "every hold is settled in the end" is checked, not only "nothing bad happens". That is how Step 3's stuck
  hold was found.
- A shortest failing order, as a readable trace, instead of a flaky test that fails once a month.
- A fix you can check before you write it in TS.
- Every behavior of a small spec replayed against the real code.

You do not get:

- A proof about the TS code. TLC checks the spec. The replay checks the code on the spec's behaviors, which is all of
  them only because this spec is tiny, and it cannot check liveness in the code.
- A free spec. You choose where the steps split. This spec splits each handler at its one `await`. If you merge steps
  that the real code keeps apart, the spec hides the bug.
- Anything the spec leaves out. Here: a `release()` that throws, and a process that crashes between setting the flag
  and calling the bank. Neither is in the spec, so TLC says nothing about them. Adding them is the next exercise, and
  it is where a durable-execution engine that retries activities earns its place.
- A familiar syntax. `/\`, `'`, `EXCEPT` and `<>` take a day to get used to. A coding agent writes them well from a
  TS function, and [Quint](/tools/quint) exists for teams who want the same checkers with a friendlier language.

</Full>

## How to start in your own project

1. Pick one flow where order matters: a signal and a timer, a retry loop, a lock, a saga with compensation.
2. Write the rules as "this must never happen" and "this must always happen in the end".
3. List the variables, including the ones outside your code: calls in flight, what each handler has read.
4. Make one action per step between two `await`s in the real code, and one action per way a call can end.
5. Say which steps are fair (timers fire, calls return) and which are not (a person may never act).
6. Run TLC with 2 or 3 actors, then dump the graph and replay it against the real code with controlled fakes.
