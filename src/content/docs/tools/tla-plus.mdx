[TLA+](https://lamport.azurewebsites.net/tla/tla.html) is a language for describing a system as state and the steps
that change it, written by Leslie Lamport. AWS, Microsoft and MongoDB use it on their distributed systems. TLA+ is the
language. The checking is done by separate tools, and there are two main ones:

- **TLC**, the original model checker. It walks every reachable state of the spec. It also checks liveness: "this
  always ends", not only "this never breaks".
- **Apalache**, a symbolic checker built on the Z3 solver. It checks every run up to a set number of steps, and handles
  large ranges of values without listing each state. It needs type annotations.

One `.tla` file works with both, which is why this is one page and not three. [Quint](/tools/quint) is a friendlier
language that compiles to TLA+ and runs these same two checkers underneath. This page uses TLA+ directly.

TLA+ describes a system as state, steps and "must never happen" rules, checked in every order. It has its own
language and checks the spec, not the real code. For tools that do the same kind of checking with the model written
in TypeScript, see [TypeScript tools](/ts-tools); for the wider field, see [Non-TypeScript tools](/tools/non-ts-tools).

<Short>Write the spec, let TLC find the bad order and the stuck key, then replay every behavior of the spec against the real TS code.</Short>

<Full>

## A separate spec, on purpose

TLA+ asks for a second, much smaller description of the system in a `.tla` file. You do not annotate your TS code.
That is extra work, and it pays back in three ways:

- Isolation. The spec has no framework, no database driver, no `async`. Only the state and the steps that matter for
  the rule. Each `await` in the real code becomes a point where the spec can switch to another step.
- Freedom. You choose what to leave out and how coarse the steps are. You can try a different design in minutes and
  check it before anyone changes production code.
- A thinking tool. To write the spec you have to name every state, every step, every "must never happen" and every
  "must eventually happen". Many design bugs show up while writing it, before TLC runs.

The cost is a second artifact to keep in step with the code. The rest of this page shows how to do that with a replay
test in vitest.

</Full>

## Why you would want this

<Short>The test passes, but two requests that miss the cache at once both query the database.</Short>

A service keeps users in memory. On a miss, `get()` loads the user from the database and keeps it:

```ts
// src/user-cache.ts
export interface User {
  id: string;
  name: string;
}

export interface Deps {
  loadUser(id: string): Promise<User>; // one database query
}

export class UserCache {
  private users = new Map<string, User>();

  constructor(private deps: Deps) {}

  async get(id: string): Promise<User> {
    const hit = this.users.get(id);
    if (hit) return hit;
    const user = await this.deps.loadUser(id);
    this.users.set(id, user);
    return user;
  }
}
```

```ts
// src/user-cache.test.ts
test('the second get() is served from the cache', async () => {
  const { db, deps } = fakeDb();
  const cache = new UserCache(deps);
  await cache.get('u1');
  await cache.get('u1');
  expect(db.queries).toBe(1);
});
```

The test passes. It lets the first `get()` finish before the second one starts. In production, a popular user's entry
expires and a hundred requests for that user arrive within the same few milliseconds. Each one misses, because none of
the loads has returned yet, and each one queries the database. This is a cache stampede. It hits the database at the
moment it is busiest. TLC tries every order.

<Full>

## When TLA+ fits

- Several actors change shared state: requests, handlers, timers, retries, queues, locks, leader election, sagas.
- The bug you fear is about order: "what if a second request arrives while the first load is in flight?"
- The rule can be said as "this must never happen" (never two loads at once) or "this must always happen in the end"
  (every request gets the user). TLC checks both kinds.

TLA+ is not the tool for proving one function's math right for every input. See the [Lean](/tools/lean) and
[Dafny](/tools/dafny) pages for that.

</Full>

## Install

<Short>One jar and Java 11 or newer. Apalache is a separate download.</Short>

TLC ships in one jar. It needs Java 11 or newer:

```sh
curl -LO https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar
java -jar tla2tools.jar Spec.tla      # runs TLC on Spec.tla with the settings in Spec.cfg
```

The jar also has SANY, the TLA+ parser, and the PlusCal translator. For the editor, install the "TLA+" extension in
VS Code: it highlights and parses specs and runs TLC from the editor.

[Apalache](https://github.com/apalache-mc/apalache) is a separate download: unpack `apalache.tgz` from its GitHub
releases and put `bin/apalache-mc` on your `PATH`. It needs Java 17 or newer. If you already use Quint, `quint verify`
has downloaded a copy into `~/.quint`.

## Step 1: describe the system as state and steps (use AI)

<Short>Variables are the state; each action says when it can happen and what the variables become.</Short>

A TLA+ spec has variables (the state) and actions (the steps that change it). An action is a list of conditions joined
by `/\` (and). A line without `'` is a condition: if it is false, the action cannot happen now. `x'` means "the value
of `x` after this step". Every action must say what every variable becomes, which is what `UNCHANGED` is for.

```text
---- MODULE UserCache ----
\* Two requests ask a cache for the same user at once. On a miss,
\* get() loads the user from the database and keeps it.
EXTENDS Naturals

Callers == {"a", "b"}

VARIABLES cached, loads, pc

vars == <<cached, loads, pc>>

Init ==
    /\ cached = FALSE
    /\ loads = 0
    /\ pc = [c \in Callers |-> "idle"]

\* get() starts: a hit returns at once, a miss awaits loadUser().
Ask(c) ==
    /\ pc[c] = "idle"
    /\ IF cached
         THEN /\ pc' = [pc EXCEPT ![c] = "done"]
              /\ UNCHANGED loads
         ELSE /\ pc' = [pc EXCEPT ![c] = "loading"]
              /\ loads' = loads + 1
    /\ UNCHANGED cached

\* loadUser() returns, and get() keeps the user.
LoadOk(c) ==
    /\ pc[c] = "loading"
    /\ cached' = TRUE
    /\ loads' = loads - 1
    /\ pc' = [pc EXCEPT ![c] = "done"]

\* loadUser() throws (a timeout, a dropped connection). get() rethrows.
LoadFails(c) ==
    /\ pc[c] = "loading"
    /\ loads' = loads - 1
    /\ pc' = [pc EXCEPT ![c] = "failed"]
    /\ UNCHANGED cached

\* The request got an error, and the client asks again.
Retry(c) ==
    /\ pc[c] = "failed"
    /\ pc' = [pc EXCEPT ![c] = "idle"]
    /\ UNCHANGED <<cached, loads>>

Next == \E c \in Callers : Ask(c) \/ LoadOk(c) \/ LoadFails(c) \/ Retry(c)

\* Requests arrive and clients retry. A load may fail, but not every time.
Spec ==
    /\ Init /\ [][Next]_vars
    /\ \A c \in Callers : WF_vars(Ask(c)) /\ WF_vars(Retry(c)) /\ SF_vars(LoadOk(c))

\* At most one database load for the user at a time.
OneLoad == loads <= 1

\* Every request gets the user in the end.
EveryoneGetsIt == \A c \in Callers : <>(pc[c] = "done")
====
```

And the config file TLC reads next to it:

```text
\* spec/UserCache.cfg
SPECIFICATION Spec
INVARIANT OneLoad
PROPERTY EveryoneGetsIt
```

How to read it:

- The variables are the whole world, not just the class: `cached` (the user is in the cache), `loads` (database
  queries in flight), and `pc` (where each request is, like a program counter).
- Two requests, `"a"` and `"b"`, are enough to show a race. `[c \in Callers |-> "idle"]` is a map, like
  `Record<string, string>`. `pc[c]` reads it, `[pc EXCEPT ![c] = "done"]` returns an updated copy.
- `Ask(c)` is an action with a parameter: one for each request. `get()` is split into steps exactly where the TS code
  has an `await`: `Ask` (the cache check and the call to `loadUser`), then `LoadOk` or `LoadFails` (how the call ends).
  `Retry` is the client asking again after an error.
- `Next` says what can happen next: any step of any request whose conditions hold. TLC tries each one.
- `Spec` is the whole system: start in `Init`, then take `Next` steps. `WF` and `SF` are fairness: requests do arrive,
  clients do retry, and a load may fail but not every time. `SF` (strong fairness) is what says "not every time": a
  load that keeps being tried succeeds in the end.
- `OneLoad` is an invariant: true in every state. `EveryoneGetsIt` is a liveness property: `<>` means "at some point".
  It says every request gets the user in the end.

## Step 2: let TLC find the bad order

<Short>TLC finds the double load in under a second, in 3 states.</Short>

`-deadlock` turns off TLC's deadlock check, since a run where both requests have the user is supposed to stop:

```text
$ java -jar tla2tools.jar -deadlock spec/UserCache.tla
Error: Invariant OneLoad is violated.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ loads = 0
/\ cached = FALSE
/\ pc = [a |-> "idle", b |-> "idle"]

State 2: <Ask line 19, col 5 to line 25, col 23 of module UserCache>
/\ loads = 1
/\ cached = FALSE
/\ pc = [a |-> "loading", b |-> "idle"]

State 3: <Ask line 19, col 5 to line 25, col 23 of module UserCache>
/\ loads = 2
/\ cached = FALSE
/\ pc = [a |-> "loading", b |-> "loading"]

6 states generated, 6 distinct states found, 3 states left on queue.
Finished in 00s
```

Read it as a timeline:

1. Request `a` misses the cache and calls `loadUser()`.
2. Request `b` arrives before that load returns. It misses too, and calls `loadUser()` again.

Two queries for one user. With a hundred requests, it is a hundred queries. TLC checks states in breadth-first order,
so the trace it prints is a shortest one. Most races need only two or three actors to show up.

## Step 3: the obvious fix, and what it breaks

<Short>Share one load per key. The stampede is gone, but TLC finds a key that fails forever.</Short>

Keep the load in flight in a second map, and let later requests await the same promise. When the load returns, keep
the user and remove the entry. This is called single-flight, or request coalescing. In the spec, the load belongs to
the map entry, not to one request, and every request waiting on it gets the same result:

```text
/\ loads = 0

State 2: <Ask line 21, col 5 to line 35, col 23 of module UserCache>

State 3: <LoadFails line 47, col 5 to line 51, col 23 of module UserCache>

/\ cached = FALSE
/\ pc = [a |-> "idle", b |-> "failed"]

State 4: <Retry line 55, col 5 to line 57, col 41 of module UserCache>
/\ loads = 0
/\ cached = FALSE
/\ pc = [a |-> "idle", b |-> "idle"]
/\ entry = "rejected"

State 5: <Ask line 21, col 5 to line 35, col 23 of module UserCache>
/\ loads = 0
/\ cached = FALSE
/\ pc = [a |-> "failed", b |-> "idle"]
/\ entry = "rejected"

State 6: <Retry line 55, col 5 to line 57, col 41 of module UserCache>
/\ loads = 0
/\ cached = FALSE
/\ pc = [a |-> "idle", b |-> "idle"]
/\ entry = "rejected"

Back to state 3: <Ask line 21, col 5 to line 35, col 23 of module UserCache>
```

Request `b` starts a load, and the database times out. `b` gets the error, but the rejected promise stays in the
`loading` map: only the success path removes it. From then on, every request finds that promise and fails at once,
without reaching the database. `Back to state 3` means the run loops forever: the user is never loaded again, until
the process restarts.

Before the fix, a failed load left nothing behind, and the next request tried again. The fix traded a stampede for a
stuck key. No test with the word "race" in its name would look for this, and an invariant cannot say it either: every
single state here is fine. Only the whole run is wrong. That is what liveness properties are for.

## Step 4: fix it properly

<Short>Remove the entry when the load ends either way. Both properties hold.</Short>

The entry must go when the load settles, whether it succeeds or fails. In the TS code that is `.finally()`. In the
spec, `LoadFails` now sets the entry back to `"none"`, like `LoadOk`:

## Step 5: the same spec in Apalache

<Short>Add a type comment to each variable; Apalache finds the same double load with Z3.</Short>

Apalache reads the same file. It needs one type comment per variable, and ignores them otherwise, so TLC still runs
the annotated file:

```text
VARIABLES
    \* @type: Bool;
    cached,
    \* @type: Int;
    loads,
    \* @type: Str -> Str;
    pc
```

On the Step 1 spec it finds the same double load, two steps in:

```text
$ apalache-mc check --no-deadlock --inv=OneLoad --length=10 spec/UserCache.tla
State 2: state invariant 0 violated.
Found 1 error(s)
The outcome is: Error
Total time: 1.321 sec
```

On the fixed spec, with `@type: Str;` added for `entry`:

```text
$ apalache-mc check --no-deadlock --inv=OneLoad --length=10 spec/UserCache.tla
The outcome is: NoError
Checker reports no error up to computation length 10
Total time: 1.834 sec
```

Clients can retry forever, so runs of this spec never stop. Apalache checked every run up to 10 steps; TLC checked
every state, which covers runs of any length. Apalache also writes a counterexample as `violation1.itf.json` in
`_apalache-out/`, the same trace format Quint uses.

Which checker to use:

| | TLC | Apalache |
|---|---|---|
| How | Lists every reachable state | Turns runs into Z3 formulas |
| Covers | Every state, however many steps | Every run up to `--length` steps |
| Liveness (`<>`, fairness) | Yes | Limited |
| Big value ranges (amounts, counters) | Slow: each value is a state | Fast: a range is one formula |
| Needs | Java 11+, one jar | Java 17+, type comments |

Start with TLC. Reach for Apalache when a variable holds amounts or large numbers and TLC's state count blows up.

## Step 6: replay every behavior against the real TS code (use AI)

<Short>TLC writes its whole state graph; vitest walks every path in it against the real class.</Short>

The spec is right. Nothing yet says the TS code behaves like the spec. TLC can write the whole state graph it
explored, with each edge labeled by its action:

```sh
java -jar tla2tools.jar -deadlock -dump dot,actionlabels spec/out/graph spec/UserCache.tla
```

That writes `spec/out/graph.dot`: one node per state, one edge per step. The spec is small, so the test can walk every
path from the first state until it stops or comes back to a state it has already been in. That is every behavior of
the spec up to its first loop, not a sample. For each path, it drives the real `UserCache` with a fake database whose
calls wait until the path says how they end:

```ts
// src/user-cache.tla.test.ts
import { readFileSync } from 'node:fs';
import { expect, test } from 'vitest';
import { UserCache } from './user-cache';

// TLC's state graph (-dump dot,actionlabels): one node per state, one edge per step.
type Status = 'idle' | 'loading' | 'waiting' | 'done' | 'failed';
interface State {
  loads: number;
  pc: Record<string, Status>;
}
interface Edge {
  to: string;
  action: string;
}

function readGraph(file: URL) {
  const states = new Map<string, State>();
  const edges = new Map<string, Edge[]>();
  let init = '';
  for (const line of readFileSync(file, 'utf8').split('\n')) {
    const node = line.match(/^(-?\d+) \[label="(.*)"(,style = filled)?\]/);
    if (node) {
      const pc = Object.fromEntries(
        [...node[2].matchAll(/(\w+) \|-> \\"(\w+)\\"/g)].map((m) => [m[1], m[2] as Status]),
      );
      states.set(node[1], { loads: Number(node[2].match(/loads = (\d+)/)![1]), pc });
      if (node[3]) init = node[1];
    }
    const edge = line.match(/^(-?\d+) -> (-?\d+) \[label="(\w+)"/);
    if (edge && edge[1] !== edge[2]) {
      edges.set(edge[1], [...(edges.get(edge[1]) ?? []), { to: edge[2], action: edge[3] }]);
    }
  }
  return { states, edges, init };
}

// Every behavior of the model: each path from the initial state until it stops,
// or until it comes back to a state it has already been in.
function allPaths(graph: ReturnType<typeof readGraph>): Edge[][] {
  const walk = (from: string, seen: Set<string>): Edge[][] => {
    const next = graph.edges.get(from) ?? [];
    if (next.length === 0) return [[]];
    return next.flatMap((e) =>
      seen.has(e.to) ? [[e]] : walk(e.to, new Set([...seen, e.to])).map((rest) => [e, ...rest]),
    );
  };
  return walk(graph.init, new Set([graph.init]));
}

// Fake database: each loadUser() call waits until the replay says how it ends.
function world() {
  const db: { caller: string; ok: () => void; fail: () => void }[] = [];
  let caller = '';
  const cache = new UserCache({
    loadUser: (id: string) =>
      new Promise((resolve, reject) => {
        db.push({ caller, ok: () => resolve({ id, name: 'Ada' }), fail: () => reject(new Error('timeout')) });
      }),
  });
  const status: Record<string, Status> = { a: 'idle', b: 'idle' };
  const ask = (who: string) => {
    caller = who;
    status[who] = 'waiting';
    cache.get('u1').then(
      () => (status[who] = 'done'),
      () => (status[who] = 'failed'),
    );
  };
  const finish = (how: 'ok' | 'fail', who: string) => {
    expect(db.length, 'the model says a load ends here, but no load is running').toBeGreaterThan(0);
    const i = Math.max(0, db.findIndex((call) => call.caller === who));
    db.splice(i, 1)[0][how]();
  };
  return { db, status, ask, finish };
}

const settle = () => new Promise((resolve) => setTimeout(resolve, 0));

// The callers whose status changes in a step. The code cannot tell a request that
// started a load from one that joined it, so both read as 'waiting'.
const changed = (from: State, to: State) => Object.keys(to.pc).filter((c) => from.pc[c] !== to.pc[c]);
const seen = (s: Status) => (s === 'loading' ? 'waiting' : s);

const graph = readGraph(new URL('../spec/out/graph.dot', import.meta.url));
const steps = (path: Edge[]) => {
  let from = graph.init;
  return path.map(({ to, action }) => {
    const who = changed(graph.states.get(from)!, graph.states.get(to)!);
    from = to;
    return { to, action, who: who[0], name: who.length === 1 ? `${action}(${who[0]})` : action };
  });
};
const paths = allPaths(graph)
  .map(steps)
  .map((path) => [path.map((s) => s.name).join(' → '), path] as const);

test.each(paths)('%s', async (_name, path) => {
  const { db, status, ask, finish } = world();

  for (const { to, action, who, name } of path) {
    if (action === 'Ask') ask(who);
    else if (action === 'LoadOk') finish('ok', who);
    else if (action === 'LoadFails') finish('fail', who);
    else if (action === 'Retry') status[who] = 'idle';
    else throw new Error(`no mapping for action ${action}`);
    await settle();

    const model = graph.states.get(to)!;
    expect(db.length, 'at most one database load at a time').toBeLessThanOrEqual(1);
    expect({ step: name, loads: db.length, ...status }).toEqual({
      step: name,
      loads: model.loads,
      a: seen(model.pc.a),
      b: seen(model.pc.b),
    });
  }
});
```

What it does for each step of a path:

- The edge label says which action ran, but not for which request. The test finds the request by comparing the two
  states: the one whose `pc` changed.
- `Ask` calls the real `get()`. It returns at once on a hit, or waits on the database.
- `LoadOk` and `LoadFails` make the waiting `loadUser()` call return or throw. If no call is waiting, the code and the
  spec disagree, and the test says so.
- After each step, the database calls in flight and each request's status must match the spec, and there must never
  be two loads at once.
- Each path is its own test, named by its steps, so a failure reads as the exact order that breaks.

First, replay the Step 1 spec against the original class. TLC stops at the first violation, so to get the full graph,
run it once with a config that leaves out the `INVARIANT` line:

```text
$ npx vitest run src/user-cache.tla.test.ts
 ❯ src/user-cache.tla.test.ts (108 tests | 80 failed)
   × Ask(a) → Ask(b) → LoadOk(a) → LoadOk(b)
   × Ask(a) → LoadFails(a) → Ask(b) → Retry(a) → Ask(a) → LoadFails(a)
   ...

AssertionError: at most one database load at a time: expected 2 to be less than or equal to 1
```

The spec has 108 behaviors up to their first loop. The real class followed the spec at every step of all of them, and
broke the rule on the 80 where both requests were waiting on the database at once. The TLC counterexample is now a
failing vitest on your real code.

After Step 4, the fixed class against the fixed spec: 68 behaviors, all pass. To check the replay is not passing by
accident, run the fixed class against the Step 3 graph: 32 of 36 fail, first at an `Ask` after a failed load. The
spec says the request fails at once; the fixed code starts a new load. The replay notices when the code and the spec
differ, not just when the rule breaks.

One thing the replay cannot do: the Step 3 class against the Step 3 spec passes all 36 behaviors. The stuck key breaks
no step and no state, only the run as a whole. TLC's `EveryoneGetsIt` check on the spec is what catches it.

## Project layout and CI

<Short>One script checks the spec and writes the graph; the replay always reads a fresh one.</Short>

One repo. The spec sits in its own folder. The graph is written from it on every test run and never committed:

```text
./
├── .github/workflows/ci.yml
├── spec/
│   ├── UserCache.tla            the spec: state, steps, OneLoad and EveryoneGetsIt
│   ├── UserCache.cfg            which spec and properties TLC checks
│   └── out/                     graph and TLC's working files, git-ignored
├── src/
│   ├── user-cache.ts            the real class
│   ├── user-cache.test.ts       normal unit tests
│   └── user-cache.tla.test.ts   replays spec/out/graph.dot against user-cache.ts
├── tools/tla2tools.jar          downloaded, git-ignored
├── .gitignore                   node_modules, spec/out/, tools/
├── package.json
└── tsconfig.json
```

Scripts in `package.json`:

```json
"scripts": {
  "tla:install": "mkdir -p tools && curl -sLo tools/tla2tools.jar https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar",
  "tla:check": "java -jar tools/tla2tools.jar -deadlock -cleanup -metadir spec/out/meta -dump dot,actionlabels spec/out/graph spec/UserCache.tla",
  "pretest": "npm run tla:check",
  "typecheck": "tsc",
  "test": "vitest run"
}
```

- `tla:install` pins the TLC version in one place.
- `tla:check` checks both properties and writes the graph in one run. `-metadir` keeps TLC's working files in
  `spec/out/` instead of a `states/` folder in the repo root.
- `pretest` runs before `npm test`, so the replay always walks the graph of the current spec. If the spec breaks a
  property, TLC exits with an error and the tests do not run on a half-written graph.

TLC and the replay both need Java, so CI is one job:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: 21
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - uses: actions/cache@v6
        with:
          path: tools
          key: tla-${{ hashFiles('package.json') }}
      - run: npm ci
      - run: test -f tools/tla2tools.jar || npm run tla:install
      - run: npm run typecheck
      - name: Check the spec, then replay every behavior against the real class
        run: npm test
```

What fails when:

| Change | Where CI fails |
|---|---|
| A spec change breaks `OneLoad` or `EveryoneGetsIt` | `npm test`, in `pretest`: TLC prints the counterexample |
| The class changes and no longer follows the spec | `user-cache.tla.test.ts`: the path and step where the code and the spec differ |
| The spec changes, the class does not | `user-cache.tla.test.ts`: the new paths no longer match the old class |
| The spec gets a new action | `user-cache.tla.test.ts`: `no mapping for action ...` |

## Making changes

<Short>Change the spec first and check it, then change the code until the replay passes.</Short>

Changing the flow (for example, cached users expire after five minutes):

1. Change the spec first: a new action, the variables it touches, and a rule if there is a new "must never happen" or
   "must always happen".
2. Run `npm run tla:check` until TLC passes.
3. Change the class. Map the new action in `user-cache.tla.test.ts` (which method to call, which call to end).
4. Run `npm test` until the replay passes. Commit the spec, the class and the replay test together.

When the graph grows: walking every path works while the spec is small. Past a few thousand paths, replay a sample.
TLC's `-simulate` mode writes random runs, and Apalache and Quint write traces as ITF JSON (see the
[Quint page](/tools/quint) for a replay built on those).

Reviewing a pull request: read the spec diff first. A new `await` in the class with no new step in the spec means the
spec no longer splits the code where it can interleave. That is the one mistake the replay cannot catch, because the
replay follows the spec's steps.

## What you get, and what you do not

You get:

- Every order of steps checked, in the spec, in under a second at this size.
- Liveness: "every request gets the user in the end" is checked, not only "nothing bad happens". That is how Step 3's
  stuck key was found.
- A shortest failing order, as a readable trace, instead of a flaky test that fails once a month.
- A fix you can check before you write it in TS.
- Every behavior of a small spec, up to its first loop, replayed against the real code.

You do not get:

- A proof about the TS code. TLC checks the spec. The replay checks the code on the spec's behaviors, which covers
  them only because this spec is tiny, and it cannot check liveness in the code.
- A free spec. You choose where the steps split. This spec splits `get()` at its one `await`. If you merge steps
  that the real code keeps apart, the spec hides the bug.
- Anything the spec leaves out. Here: more than one key, entries that expire, and a second server process with its
  own cache. None of them is in the spec, so TLC says nothing about them. Two processes are the next exercise: each
  one coalesces its own requests, and the database still gets one query per process.
- A familiar syntax. `/\`, `'`, `EXCEPT` and `<>` take a day to get used to. A coding agent writes them well from a
  TS function, and [Quint](/tools/quint) exists for teams who want the same checkers with a friendlier language.

</Full>

## How to start in your own project

1. Pick one flow where order matters: a cache, a signal and a timer, a retry loop, a lock, a saga with compensation.
2. Write the rules as "this must never happen" and "this must always happen in the end".
3. List the variables, including the ones outside your code: calls in flight, what each request has seen.
4. Make one action per step between two `await`s in the real code, and one action per way a call can end.
5. Say which steps are fair (requests arrive, calls return) and which are not (a call may fail).
6. Run TLC with 2 or 3 actors, then dump the graph and replay it against the real code with controlled fakes.
