[Polygraph](https://github.com/cognitive-fab/polygraph) adds a check to the reducers you already have: Redux, Zustand,
a `switch` on `action.type` inside a checkout or a workflow. You keep the code as it is. An LLM reads it and writes a
copy as a JavaScript state machine, and a model checker tries every action in every state the copy can reach, and
reports the first state that breaks a rule you wrote, with the shortest list of actions that gets there.

In return you get what your tests cannot give: the orders of actions you did not think of, all of them, over the
actions and values you list. You write nothing but the rules. It is a CLI and a Claude Code plugin.

The catch: the copy is a copy. It has the same bugs as your code, so only your rules catch them, and the checker tries
only the values that were listed for it. Below: the coupon bug it finds, the discount bug it misses, and whether it
beats [fast-check](/typescript-formal-methods/fast-check), which checks the same rules on the real code with no copy.

[TLA+](/formal-methods/tla-plus), [Quint](/formal-methods/quint), [pnueli](/typescript-formal-methods/pnueli) and
[stifinder](/typescript-formal-methods/stifinder) run the same kind of check on a model you write yourself.
[XState](/typescript-formal-methods/xstate) and [effect-machine](/typescript-formal-methods/effect-machine) walk a
machine that is the code. Polygraph is the only tool on this site where the model is written for you.

## Case studies

<Tabs>
<TabItem label="A coupon that stays after the cart shrinks">

A shop's cart is a reducer. Every item costs 10.00, and the `SAVE5` coupon needs a total of at least 20.00:

```ts
// cart.ts
export function cart(state: Cart, action: CartAction): Cart {
  switch (action.type) {
    case 'ADD_ITEM':
      if (state.items === MAX_ITEMS) return state;
      return { ...state, items: state.items + 1 };
    case 'REMOVE_ITEM':
      if (state.items === 0) return state;
      return { ...state, items: state.items - 1 };
    case 'APPLY_COUPON':
      if (action.code !== 'SAVE5') return state;
      if (state.items * PRICE < MIN_SPEND) return state;
      return { ...state, coupon: 'SAVE5' };
  }
}
```

The minimum is checked when the coupon is applied, and never again. Add two items, apply the coupon, remove one item:
the coupon stays on a 10.00 cart. A test with those four actions shows it:

```ts
// cart.coupon.test.ts
test('the coupon goes when the cart drops under the minimum', () => {
  const actions: CartAction[] = [
    { type: 'ADD_ITEM' },
    { type: 'ADD_ITEM' },
    { type: 'APPLY_COUPON', code: 'SAVE5' },
    { type: 'REMOVE_ITEM' },
  ];
  const state = actions.reduce(cart, emptyCart);
  assert.equal(state.coupon, null);
});
```

```text
✖ the coupon goes when the cart drops under the minimum
AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
'SAVE5' !== null
```

To write that test you have to think of those four actions in that order. With twenty actions and ten fields, nobody
does.

### In Polygraph

You write one file, the rules. Each rule is a function of the state that must always be true:

```js
// invariants.mjs
export const stateInvariants = [
  { name: 'coupon-needs-minimum-spend', pred: (s) => s.coupon === null || s.items * 1000 >= 2000 },
];
```

The model comes from the LLM: it reads `cart.ts` and writes it again as a state machine, one function per action.
That step needs an Anthropic API key and, the README says, Opus 5 or better; we wrote the file by hand in the same
format. A small `contract.json`, yours, names the state fields, the actions and the values to try. Then the check:

```sh
node node_modules/@cognitive-fab/polygraph/scripts/check.mjs --spec specs/cart-sam.js --contract contract.json \
  --invariants invariants.mjs
```

```text
states explored: 8
rejections explored: below-minimum ×4, cart-empty ×2, cart-full ×2, unknown-code ×8
1 invariant violation(s):

  ✗ coupon-needs-minimum-spend [state] — reachable state violates the rule
    counterexample (shortest path from init):
      init            {"items":0,"coupon":null}
      ADD_ITEM({}) -> {"items":1,"coupon":null}
      ADD_ITEM({}) -> {"items":2,"coupon":null}
      APPLY_COUPON({"code":"SAVE5"}) -> {"items":2,"coupon":"SAVE5"}
      REMOVE_ITEM({}) -> {"items":1,"coupon":"SAVE5"}
```

The same four actions, found from the rule alone. The fix is in `REMOVE_ITEM`: drop the coupon when the total falls
under the minimum. On the fixed code the check explores 6 states and reports "no invariant violations reachable".

The point that is easy to miss: the LLM's copy has the bug too. Polygraph's other check, replay, runs your real
reducer through a few recorded sessions and compares every call with the copy. Here all 15 calls match, on the buggy
code and on the fixed code. Replay tells you the copy is faithful to the code. It cannot tell you the code is right;
only your rule does. The code, the spec and the tests are in
[formal-methods-samples/polygraph-coupon](https://github.com/speccraft-io/speccraft-io/tree/main/formal-methods-samples/polygraph-coupon).

<TabItem label="Where it stops: a discount that goes negative">

The same cart, now with a percentage discount. Two coupons used together can add up to more than 100 percent:

```ts
// cart.ts
export function cart(state: Cart, action: CartAction): Cart {
  switch (action.type) {
    case 'ADD_ITEM':
      if (state.items === MAX_ITEMS) return state;
      return { ...state, items: state.items + 1 };
    case 'APPLY_DISCOUNT':
      return { ...state, percent: action.percent }; // two coupons together can pass 100
  }
}

export const total = (c: Cart) => Math.round((c.items * PRICE * (100 - c.percent)) / 100);
```

```ts
// cart.negative.test.ts
test('the total is never negative', () => {
  const state = cart(cart(emptyCart, { type: 'ADD_ITEM' }), { type: 'APPLY_DISCOUNT', percent: 150 });
  assert.ok(total(state) >= 0, `total is ${total(state)}`);
});
```

```text
✖ the total is never negative
AssertionError [ERR_ASSERTION]: total is -500
```

### In Polygraph

The rule is one line, `total-never-negative`. The checker tries every action in every state, but "every action" means
every action with every value on its list. The list comes from the contract, so you pick it; here it is 10 and 50:

```js
// specs/cart-sam.js
APPLY_DISCOUNT: {
  action: (data = {}) => ({ ...data }),
  schema: { percent: { type: 'number' } },
  // The values the model checker tries, copied from the contract.
  domain: [{ percent: 10 }, { percent: 50 }],
},
```

```text
states explored: 12
rejections explored: cart-full ×3
no invariant violations reachable ✓
```

Passed, and the total still goes negative at 150. Put 150 on the list and the check finds it in one step. But the bug
is at the value nobody listed, and Polygraph's README says so itself: no check measures the gap between the listed
values and real data. A rule about a number needs a tool that proves it for every number: [Lean](/formal-methods/lean)
does exactly this case, and [Dafny](/formal-methods/dafny) and [LemmaScript](/typescript-formal-methods/lemmascript)
do the same for functions written in a TypeScript shape. The code and the spec are in
[formal-methods-samples/polygraph-discount](https://github.com/speccraft-io/speccraft-io/tree/main/formal-methods-samples/polygraph-discount).

## Conclusion

How Polygraph compares with the other tools for the same job: the idea is good, but today it is not the tool to pick,
for three reasons.

1. fast-check does the job on the real code. We gave it the same rule and random lists of the same three actions on
   the real reducer, no copy, no LLM, no key. At its default of 100 runs it found the same four-step counterexample
   in 18 of 20 tries, in about 2 ms each. What Polygraph adds is "every reachable state, not a random sample". That
   matters for a big reducer, and for a big reducer the values you can list matter more, as the second case shows.
2. The copy is the weak spot. It costs an API call to a strong model on every change to the code, and it inherits the
   code's bugs. Replay checks the copy against the code, not the code against what you meant.
3. TLA+ and Quint cover what it cannot: several processes, messages, crashes and retries in every order, and rules
   about what must eventually happen. Polygraph checks one machine, one action at a time, with rules on one state or
   one step. Its own README sends you to Specula for deep bugs in large concurrent or distributed systems.

Comparison with the other tools:

Both Polygraph and fast-check handle:

- A rule that holds when it is set and breaks after a later action, like the coupon.
- A field that is reset by one action and forgotten by another.
- A step allowed in a state where nobody expected it, like a refund after a cancel.

Only TLA+, Quint, pnueli and stifinder handle:

- Two workers on the same order, and what each one sees.
- A crash in the middle of a step, and what the restart sees.
- "Every order is eventually paid or refunded", not only "never charged twice".

Only Lean, Dafny and LemmaScript handle:

- A rule about a number that must hold for every number, like the discount.

The idea has a future, and the proof is not Polygraph. Specula, a research project that does the same three steps in
TLA+ (an LLM writes the model, a model checker checks it, real traces validate it), reports 249 bugs in 48 projects
such as MongoDB and etcd, 68 of them confirmed by the maintainers. Polygraph's own README calls Specula the closest
project and ahead on evidence. What Polygraph has that Specula does not is JavaScript: the model is a JavaScript file
and the checker runs in Node, and as a Claude Code plugin it records the calls and builds the test doubles for you. Whether one person carries that to something teams use is open. For a reducer you have today, fast-check;
for concurrency and "eventually", TLA+ or Quint; for a rule about numbers, Lean, Dafny or LemmaScript. Polygraph is
worth a look for the idea, not yet for the job.
